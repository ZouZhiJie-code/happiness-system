# 板块 7A｜单任务端到端聊天 A/B 运行确认包

版本：`2026-08-06.board7a-chat-e2e-ab-v1`

状态：`方法已确认；等待用户事实卡；模型调用 0`

适用决定：`GI-082｜单任务双分支端到端验证方法`

## 1. 本轮为什么这样验证

六题真实输出中的 H1、H2、H3、T3 都预置了非当前候选产生的 AI 回合，只能观察候选接手既定上下文后的局部表现。本轮让两个候选从同一段真实用户材料开始，各自完成后续访谈，直接观察提问方向、认识结果、用户负担和控制执行。

两个分支只共享起点、用户事实边界、产品规则、模型参数和评价标准。后续问题与用户回答允许自然分叉；分叉本身属于待评测的候选行为。

## 2. 已确认范围

1. 只使用 `1` 个真实【陪我聊】任务。
2. 共同起点为：用户已经选择【陪我聊】，并提供第一段实质性材料；共同起点之前只允许固定、中性的产品入口。
3. 两个候选以匿名分支甲、乙运行，架构身份在两条分支完成盲评前保持封存。
4. 两条分支分别保存完整上下文；用户只根据当前分支已发生的对话自然回复。
5. 用户回复只进入对应分支，不把另一分支的问题、回答或新认识带入当前分支。
6. 每次用户输入只触发当前分支的一次用户可见 AI 回合；系统不自动连续推进。
7. 本轮终点为访谈结果形成，暂不进入日志生成、编辑或保存。
8. 产品负责人完成最终体验裁决；Codex 独立初评与产品裁决分开保存。

## 3. 候选与共同运行条件

| 项目 | 固定值 |
|---|---|
| 候选 A | 单次结构化生成，同时完成语义判断与用户可见回应 |
| 候选 B | 先形成结构化语义，再根据冻结语义和引用原话生成用户可见回应 |
| 模型 | `deepseek-v4-flash` |
| 温度 | `0.2` |
| Thinking | 关闭 |
| 质量重试 | `0` |
| 共同输入 | 相同产品规则、模式和第一段用户材料 |
| 分支输入 | 当前分支自己的完整对话，不共享另一分支后续内容 |
| Production | `legacy + baseline`，保持原样 |

正式运行前需要基于已填写用户事实卡冻结完整 Prompt、模型参数、匿名映射和包指纹。此前六题候选的 Prompt 只作为结构起点；端到端包需要明确向两个候选提供相同的三阶段产品目标，并让候选依据本分支完整语境自主判断当前动作。

## 4. 用户事实卡

[用户事实卡](./board7a-chat-e2e-ab-v1-user-fact-card.md)分成两层：

- 模型可见：共同的第一段用户材料。
- 仅供评测：用户真实目标、已知事实和感受、不确定内容、表达边界和成功标志。

用户事实卡用于保持两个分支来自同一个真实用户状态。它不向模型泄露标准答案，也不规定候选必须提出哪一个问题。

## 5. 逐轮交互方式

1. 运行器随机决定匿名分支甲、乙对应的候选，并封存映射。
2. 两个分支同时从用户事实卡中的第一段材料开始。
3. 每次只展示一个匿名分支的当前 AI 回应。
4. 产品负责人在对话外选择：
   - `继续回答`：只依据当前分支和用户事实卡自然输入下一句话；
   - `已达到终点`：封存当前分支，进入盲评；
   - `因质量问题停止`：封存当前分支并记录停止原因。
5. `继续回答`时，输入只写入当前分支并触发该分支下一轮；另一分支保持原状态。
6. 一个分支结束后，另一个分支可以继续，直到也形成终点或被产品负责人停止。
7. 两个分支均结束后，先完成整体盲评，再揭晓架构与结构化语义。

对话外的三个选择只属于评测控制，不进入用户可见产品方案，也不改变 GI-080 已冻结的正式交互边界。

## 6. 分支终点

| 结果 | 终点条件 |
|---|---|
| `value_success` | 候选形成一条有用户来源、可纠正并回应初始目标的认识；产品负责人判断当前程度已经说清楚 |
| `qualified_pause` | 材料有限、继续价值不高或用户不想继续；候选忠实保留当前范围并自然停住 |
| `user_control_exit` | 用户明确停止、结束或要求生成日志；候选正确执行控制。本轮到执行控制为止，不运行日志链路 |
| `quality_failure` | 候选偏离焦点、重复索取、持续低价值推进或造成产品负责人因质量终止 |
| 单例阻断 | 出现纠正失效、来源编造、模式污染、明确停止后继续追问等问题时立即停止分支；阻断标记与四类结果分开保存 |

候选输出成果或暂停后，产品负责人可以继续自然输入。只有评测层的“已达到终点”会封存分支；候选无需为了评测追加确认问题。

## 7. 最小裁决口径

两条路径允许不同，最终使用同一结果尺度比较：

1. 初始用户目标是否得到回应；
2. 焦点是否来自用户并随纠正更新；
3. 下一问是否值得回答；
4. 最终认识是否准确、有来源、可纠正；
5. 用户投入与对话负担是否合理；
6. 停止、纠正和其他用户控制是否执行；
7. 是否出现普通失败或单例阻断；
8. 到达终点所需的提问数、用户回答数和时间，只作为过程证据。

问题更少不自动获得更高评价。不同路径都形成合格结果时，可以判为两者相当。

## 8. 偏差控制

1. 运行前冻结用户事实卡，两个候选使用同一初始用户状态。
2. 匿名映射和展示顺序随机化，盲评完成前保持封存。
3. 产品负责人回答时只读取当前分支；另一分支内容不进入本分支事实。
4. 某个分支自然形成的新认识只属于该分支，作为该候选带来的结果保存。
5. 两条分支结束前不填写相对评分，减少过程中的比较性修正。
6. 单任务只承担高信号诊断。两者接近时保持平局，再决定是否补第二个任务。

真人先后体验带来的影响仍会保留在局限说明中。本轮不把单条轨迹写成跨场景稳定性证明。

## 9. 建议运行预算

| 项目 | 建议值 |
|---|---:|
| 基础生成请求上限 | `18` |
| 全批技术失败重试上限 | `3` |
| 质量重试 | `0` |

候选 A 的一个用户可见回合使用 `1` 次基础请求；候选 B 使用 `2` 次。两个分支都继续时，一组对应回合共使用 `3` 次基础请求。`18` 次能够覆盖最多六组双分支回合；一个分支提前结束后，剩余额度可以供另一分支继续。

该预算只约束本次评测资源，不形成产品问题数量上限。预算耗尽时立即暂停并记录 `evaluation_budget_exhausted`，由产品负责人决定是否追加独立预算。

## 10. 运行后交付

1. 两个匿名分支的完整对话与逐轮结构化语义；
2. 每轮调用、Trace、耗时、Token、技术错误和重试记录；
3. 产品负责人整体盲评；
4. Codex 独立初评；
5. 架构揭晓、结果对照、分歧和方法局限；
6. 是否已经获得架构方向证据，或继续保持平局。

## 11. 当前停止点

当前需要产品负责人提供用户事实卡中的两项必填内容：

1. 想真实聊的一件事，用准备发给 AI 的第一段话表达；
2. 希望这次聊天最终帮自己弄清楚什么。

Codex 会根据这两项先整理事实卡候选，再交由产品负责人确认。事实卡、Prompt、匿名映射、预算和包指纹全部冻结后，才提交独立模型运行授权。当前模型调用保持 `0`。

Production、线上 Prompt、API、页面、数据库、配置和运行开关继续保持原样。
