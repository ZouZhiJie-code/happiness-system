# 节点六：追问目标规划

> 事实口径：本文依据 2026-07-20 工作区当前代码核对，面向非技术背景 AI 产品经理。

## 核心结论

动作决策层先决定“这一轮继续提问”；追问目标规划层进一步决定“这一轮围绕当前事件补哪一类信息、用户适合用什么形态回答”。它把阶段和事件档案整理成一份内部问题规格 `questionSpec`，供后续 Prompt 组装、问题表达、服务端检查和会话恢复共同使用。

这几个节点的职责边界如下：

- 动作决策层：决定继续追问、进入选择、低压收束或维度转向。
- 追问目标规划层：定义本轮提问目标、轮次意图、表达难度和事件锚点。
- Prompt 组装层：把问题规格与对话、档案、理论规则一起提供给模型。
- 模型生成层：形成思路摘要和最终中文问题。
- 服务端检查层：检查问题是否清楚、重复或偏离目标，必要时改写。

当动作决策已经进入事件完成或维度转向时，本层输出为空，系统直接展示选择卡。

## 1. 为什么存在

访谈阶段只能描述大方向。例如 `probe_pattern` 统一表示“继续提炼”，它在不同维度中可能对应值得感标准、判断线索、下次小动作或关系信号。系统还需要一层更细的规划，才能把“继续提炼”转成一轮可执行的问题目标。

这一层解决三个产品问题：

1. **确定提问焦点**：在事件、直接反应、原因证据和稳定线索之间选择一个目标。
2. **控制回答负担**：确定采用常规表达、简化表达或具体锚点表达。
3. **保持当前事件连续性**：把用户已经说过的事件片段带入下一问，减少话题漂移。

因此，本层相当于访谈中的“问题任务单”。它规定这一问要完成什么任务，后续节点再完成上下文注入和自然语言表达。

## 2. 输入

| 输入 | 当前用途 |
|---|---|
| 动作决策结果 | 只有继续追问、继续深挖或问题修复会进入问题规划 |
| 当前维度 | 决定目标选择规则和维度细分规则 |
| 当前访谈阶段 | `collect_event` 会优先寻找具体事件，其余阶段结合事件档案判断 |
| 最新事件档案 | 判断事件、感受、原因和线索等信息是否已经出现 |
| 上一轮问题规格 | 继续深挖和问题修复时保留原来的提问方向 |
| 修复信号 | 决定下一问采用简化表达或具体锚点表达 |
| 感谢维度证据状态 | 避开用户已经否认的需要、感谢原因或关系假设 |

## 3. 内部逻辑 / 优先级

### 3.1 先确定本轮属于哪种提问意图

当前共有三种 `stageIntent`：

| 内部值 | 产品含义 | 主要场景 |
|---|---|---|
| `advance` | 正常推进 | 用户刚提供了新的访谈内容 |
| `resume` | 继续当前事件 | 用户在完成选择后点击“继续深挖” |
| `repair` | 修复当前问题 | 用户表示问题难懂、太抽象或希望换个角度 |

`resume` 和 `repair` 会优先继承上一问题的目标，保持同一条访谈任务。问题修复还会累计 `repairCount`：第一次通常采用简化表达，第二次进入具体锚点表达；第三次由动作决策层进入低压选择，本层不再输出新的问题规格。用户明确要求“换个角度”时，第一次修复也可以直接进入具体锚点表达。

### 3.2 再选择一个通用问题目标

目标选择优先级是：

1. 服务端为特殊场景明确指定的目标
2. 继续深挖或修复时沿用上一问题目标
3. 根据当前维度、阶段和事件档案自动推导

当前通用目标共有五类：

| 通用目标 | 产品含义 |
|---|---|
| `event_anchor` | 找到或补清具体事件、画面或瞬间 |
| `prior_assumption` | 了解用户之前自然持有的想法或判断 |
| `reaction_evidence` | 补充当时直接出现的感受、反应、念头或状态变化 |
| `insight_evidence` | 补充原因、关键证据或新理解 |
| `judgment_clue` | 提炼可继续使用的标准、判断、关系或行动线索 |

其中，`collect_event` 阶段固定选择 `event_anchor`。其他阶段主要依据档案中的信息缺口选择目标。

`prior_assumption` 已进入问题规格类型。正常自动推导路径当前集中覆盖其他四类目标；现有代码主要在恢复缺少结构化规格的历史问题时，根据旧问题中“原来、之前、以前”等词识别 `prior_assumption`。

### 3.3 应用维度细分规则

通用目标只描述提问层次。维度规则进一步确定该目标在当前产品理论中的实际含义。

感谢维度拥有额外的 `subTarget`：

1. 缺少对方的具体行动：`kind_action`
2. 行动已存在，优先补被看见的需要：`seen_need`
3. 需要已被否认或仍缺感谢原因：`gratitude_reason`
4. 前述材料成立后：`relationship_signal`

感谢维度还会附带 `hypothesisKey`，支持后续记录用户确认或否认了哪一种推断。

思考维度有一项服务端特殊保护：用户已经对场景问题进行修复、当前仍缺判断变化时，后续正常推进可以强制使用 `insight_evidence + concrete_anchor`，继续询问具体顾虑、画面或念头，避免重新回到同一个场景问题。

### 3.4 补全回答形态和事件锚点

问题规格还包含两个重要控制项：

- `surfaceLevel`：`default / simplified / concrete_anchor`，代表常规、简化和具体锚点三种表达层级。
- `anchorText`：从当前事件档案中选取一段用户材料，经过清理和安全截短后带入下一问。

锚点来源存在维度差异：

- 感谢：优先使用感谢时刻，其次使用对方行动，再使用通用事件字段。
- 改进：优先使用事件，其次使用具体卡点或重复条件。
- 开心、充实、思考：使用通用事件字段。

### 3.5 部分目标会继续转成“问法意图包”

当后续走确定性的结构化问题表达路径时，`reaction_evidence / insight_evidence / judgment_clue` 会再被转换成一个更贴近用户回答方式的意图：

- 回答直接感受
- 指出一个关键点
- 留下一句话
- 给出下次可观察的线索

这个意图包还固定要求：一轮只完成一个认知动作、围绕当前事件、尽量使用用户原有词语，并让答案可以落成具体例子或一句话。

## 4. 五维差异

| 维度 | 正常自动目标路径 | 当前规划重点 |
|---|---|---|
| 开心 | 具体开心时刻 → 直接状态反应 → 开心来源或意义 → 个人快乐线索 | 五个维度中唯一把 `reaction_evidence` 作为常规独立目标的维度 |
| 充实 | 具体经历 → 进展证据 → 值得感标准 | `judgment_clue` 在问法意图中会转成“留下一句话”；规划层主要按字段是否存在判断，可信度由后续检查补充 |
| 思考 | 触发片段 → 新理解证据 → 判断线索 | 支持场景问题修复后的具体锚点保护；`prior_assumption` 当前属于可用目标，正常路径较少主动触发 |
| 改进 | 具体情境 → 卡点或重复条件 → 可继续使用的行动线索 | 改进轨道、状态判断、可控因素和下次尝试在通用规格中被压缩为 `insight_evidence / judgment_clue` 两类目标 |
| 感谢 | 感谢时刻 → 对方行动 → 被看见的需要或感谢原因 → 关系线索 | 同时输出通用目标与专属 `subTarget`，并读取否认证据调整方向 |

## 5. 输出

本层的主要输出是 `questionSpec`：

| 字段 | 产品含义 |
|---|---|
| `target` | 这一轮要补充的通用信息层次 |
| `subTarget` | 感谢维度的具体追问对象 |
| `hypothesisKey` | 感谢维度正在验证的推断方向 |
| `stageIntent` | 正常推进、继续深挖或问题修复 |
| `surfaceLevel` | 常规、简化或具体锚点表达 |
| `anchorText` | 下一问应围绕的用户事件片段 |
| `repairCount` | 当前问题已经经历的修复次数 |

部分确定性问题表达还会生成 `AskIntentEnvelope`，其中包含回答形态、认知负担和“保持当前事件”等约束。

`questionSpec` 会进入三个下游位置：

1. 交给 Prompt 组装层，作为模型生成问题的明确提示。
2. 附在最终 AI 消息的内部载荷中，供下一轮证据判断和问题修复读取。
3. 供服务端检查层核对最终问题是否符合目标，并在需要时重新生成问题规格。

## 6. 用户可见结果

用户看不到问题规格、目标名称和内部字段。用户能感受到的结果主要体现在下一问：

- 问题继续围绕刚才的事件。
- 每次聚焦一个回答任务。
- 问题会从“具体发生了什么”逐渐走向“为什么重要”和“留下了什么线索”。
- 用户反馈难懂后，问题会变短、变具体，并继续围绕原来的提问目标。
- 感谢维度会避开用户已经否认的需要或关系解释。

举例：思考维度已经有触发片段和新理解、仍缺稳定判断时，规划结果通常是：

```text
target: judgment_clue
stageIntent: advance
surfaceLevel: default
anchorText: 用户刚才讲述的事件片段
```

后续节点才会把它表达成自然中文问题。

## 7. 当前问题

### 7.1 通用目标与维度槽位的颗粒度存在差距

五类通用目标需要承载五个维度的大量专属字段。改进维度中的改进轨道、状态判断、可控因素和下次尝试，当前主要汇入两个通用目标。仅查看 `questionSpec`，难以准确知道本轮正在补哪个专属槽位。

### 7.2 部分目标按照“字段存在”判断

开心、充实、思考和改进的常规目标推导主要检查字段是否已有文本。字段的可信度、证据强弱和语义质量通常交给后续维度规则与服务端检查处理。因此，规划结果仍可能在后续被改写。

### 7.3 五个维度的证据感知程度不同

感谢维度已经能用确认、弱证据和否认证据细分追问目标。其他维度主要使用快照字段和阶段判断，复杂纠正对目标选择的影响较弱。

### 7.4 `prior_assumption` 的正常触发范围有限

该目标已进入统一类型和问题修复能力，正常自动推导函数当前的分支集中在其他四类目标。思考维度 Prompt 中包含“原来的疑问或判断”这一访谈顺序，目标规划层对这一层的显式表达仍较弱。

### 7.5 规划职责分布在多个位置

通用目标由问题协议推导，维度具体追问顺序还存在于访谈引擎和 Prompt 规则中，充实等维度又有服务端专属校验。最终问题的真实目标可能经历“先规划、模型表达、服务端再校正”的变化，产品分析需要同时查看多处规则。

### 7.6 继续深挖和修复会优先继承上一目标

这一机制保证对话连续性，也会让上一轮已经偏离的目标继续保留。当前系统依靠感谢否认保护、思考场景保护、重复问题检查和问题质量门在后续环节修正。

### 7.7 当前存在两套问题规划表达

`questionSpec` 覆盖所有问题；`AskIntentEnvelope` 主要服务直接反应、原因证据和判断线索三类结构化表达。事件锚点和先前判断继续使用其他问法路径。因此，完整理解“这一问为什么这样问”需要同时查看目标规格和具体表达路径。
