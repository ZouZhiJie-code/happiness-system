# 节点八：模型生成

> 事实基准：2026-07-20 当前代码。本文只解释现有功能设计，不展开优化方案或后续行动。

## 一、结论总览

模型生成层的职责是：**在服务端已经确定访谈方向和本轮问题目标之后，把结构化上下文转成自然、可读的一轮对话表达。**

这一层的访谈输出只有两项用户可见内容：

1. `thinkingSummary`：一到两句浅色思路摘要，用来呈现系统如何理解用户刚才的回复，以及当前关注的重点。
2. `question`：一个具体、开放式的正式追问。

访谈阶段、完成判断、选择卡、维度转向和停止边界均由服务端规则提前决定。模型生成路径只会在系统已经决定“继续追问当前事件”时运行。问题修复、事件完成、材料不足收束和维度转向都可以直接形成服务端回复，跳过本层模型调用。

在一次正常且有内容的用户回复中，系统通常存在两次彼此独立的模型调用：

- 前一次是结构化槽位抽取，归属于节点二。
- 后一次是本节点的思路摘要和追问生成。

两次调用共用 Chat Provider 运行时，使用不同 Prompt、输出协议和参数。

---

## 二、为什么存在这一层

前几个节点已经得到三类确定信息：

- 当前事件已积累了哪些事实；
- 访谈目前处于哪个阶段；
- 下一轮需要补充哪个目标。

这些内部结果仍然属于产品控制语言，例如“继续当前事件”“目标是判断线索”“使用具体锚点”。用户需要看到一段贴合自己表达的自然中文。因此，本层承担两项语义表达工作：

1. 把最新材料解释成简短、可见的理解摘要。
2. 把问题目标组织成用户容易回答的单一问题。

这层保留了大模型在语义理解和语言表达上的灵活性，同时将流程权限保留在服务端规则中。

---

## 三、模型承担的任务与权限边界

### 3.1 模型实际承担的任务

- 阅读当前维度、阶段、事件档案和最近对话；
- 理解用户最新回复中的语义重点；
- 生成简短的 `thinkingSummary`；
- 根据 `questionSpec` 和维度规则生成一个自然追问；
- 在继续深聊时，围绕当前事件自然延续或换一个切口。

### 3.2 服务端保留的控制权

以下内容由服务端预先决定或在模型返回后固定写入：

- 当前访谈维度和阶段；
- 本轮问题目标 `questionSpec`；
- 是否继续追问；
- 是否结束当前事件；
- 是否展示选择卡；
- 是否转向其他维度；
- 当前轮属于 opening、digging、closing 或 choice；
- 已覆盖的访谈深度；
- 模型失败时使用的确定性问题。

当前生成函数写入的 `stateUpdate` 固定为继续访谈语义：`shouldEndDimension=false`、`offerChoice=false`。所以模型输出无法直接结束维度或开放日志生成。

### 3.3 相邻功能边界

- **结构化槽位抽取**：调用同一类 Chat Provider，输出 JSON 并经过 Schema 校验，归属于节点二。
- **Prompt 组装**：决定模型能看到哪些上下文和规则，归属于节点七。
- **服务端检查与改写**：检查重复、抽象、否认冲突和摘要质量，归属于节点九。
- **日志草稿生成**：使用独立 Prompt、JSON Schema、质量门和 fallback，属于后续日志链路。

---

## 四、输入是什么

本层主调用接收的输入可以分为六组。

### 4.1 当前任务

- 维度：开心、充实、思考、改进、感谢；
- 动作：普通回复 `reply` 或继续深聊 `continue_current_event`；
- 目标阶段；
- 本轮 `questionSpec`。

### 4.2 当前事件材料

- 最新 `snapshot`；
- 当前活动事件；
- 会话里的全部事件摘要；
- 当前事件已经覆盖的访谈视角。

### 4.3 对话材料

- 用户最新回复；
- 最近可读对话；
- 最近几轮 Assistant 的结构化输出；
- 当前回复是否被判断为有效内容。

### 4.4 进度信息

- 会话总有效轮数；
- 当前事件有效轮数；
- 上一轮与本轮建议覆盖的访谈深度；
- 当前探索轮次覆盖的视角。

### 4.5 语义解释和维度规则

- 当前材料在该维度中的主题；
- 理论摘要和后续关注点；
- 防止内容被写浅的提醒；
- 五个维度各自的提问顺序和禁区。

### 4.6 可选长期记忆

服务层会先尝试读取与当前用户、维度和事件相关的长期记忆。读取成功时，格式化后的 `memoryContext` 会进入问题 Prompt；读取失败时，本轮继续使用会话内材料。

## 五、当前调用与生成流程

### 5.1 判断本轮是否进入模型生成

服务层先检查当前回复是否已经由确定性分支处理。

以下场景会直接返回预制 Assistant Turn：

- 用户请求生成日志；
- 用户触发停止边界；
- 用户请求简化或更换问题；
- 当前事件达到完成选择；
- 开心维度触发转向建议；
- 用户切换到下一个事件并获得新开场问题。

当 `assistantAction` 为 `reply` 或 `continue_current_event` 时，系统才会进入问题生成调用。

### 5.2 选择运行时 Provider

`getAIProvider("chat")` 会解析当前 Chat Provider 配置：

1. 优先读取已发布且可用的数据库运行时配置；
2. 数据库配置停用、读取失败或缺少发布配置时，读取环境变量中的火山方舟配置；
3. 运行时工厂支持 OpenAI、Anthropic、Volcengine Ark 三种 Provider；
4. 当前只选择一个可用 Provider 执行本轮请求。

仓库生产事实中记录的环境兜底路径为 Volcengine Ark 直连模型，模型标识为 `deepseek-v3-2-251201`。数据库存在有效发布配置时，运行时会采用数据库配置。

### 5.3 调用模型

追问生成参数固定为：

- `temperature: 0.45`
- `maxTokens: 500`

系统根据接口形态选择调用方式：

- 流式接口且 Provider 支持 `stream`：先尝试流式调用；
- 普通接口：直接调用一次 `complete`；
- 流式尝试失败：再使用同一 Provider 执行一次非流式 `complete`。

这里的请求级重试保持在同一个 Provider 内。跨 Provider 选择发生在请求开始前的运行时配置解析阶段。

### 5.4 解析模型文本

Prompt 要求模型严格输出：

```text
<<SUMMARY>>一到两句思路摘要<<QUESTION>>一个具体追问
```

流式解析器会跨数据分片识别标记，并将文本拆成：

- `thinkingSummary`
- `question`

它同时兼容历史标记 `<<INSIGHT>>`，并将其映射为 `thinkingSummary`。

当模型未输出标记时，解析器会把整段文本作为 `question`，`thinkingSummary` 留空。只要摘要或问题中至少一项有内容，本次模型调用就被记录为有效输出。

### 5.5 组装 Assistant Turn

模型文本返回后，服务端会：

1. 优先沿用上游已经生成的 `questionSpec`；
2. 上游缺少 `questionSpec` 时，根据模型问题反推一个规格；
3. 使用问题表层协议，把候选问题落实为符合当前目标和表达层级的问题；
4. 将摘要限制在 180 字以内，问题限制在 160 字以内；
5. 固定填充 `analysis`、`stateUpdate`、`meta.depthReached` 等内部字段；
6. 把完整 Assistant Turn 交给节点九继续检查和改写。

因此，模型直接生成的是两个文本片段。完整的 `AssistantTurnPayload` 是由服务端组装形成的。

## 六、输出协议

### 6.1 模型原始输出

| 片段 | 用途 | Prompt 约束 |
|---|---|---|
| `thinkingSummary` | 用户可见的浅色思路层 | 1–2 句、避免问句、避免系统口吻、避免机械复述 |
| `question` | 本轮唯一正式追问 | 一个开放式问题、贴近当前事件、推进未覆盖目标 |

### 6.2 服务端组装后的输出

完整 Assistant Turn 包含：

- `insight`：当前生成路径固定为空；
- `thinkingSummary`：模型摘要或后续确定性摘要；
- `analysis`：服务端生成的内部说明；
- `question`：经过问题表层协议处理后的正式问题；
- `questionSpec`：问题目标、表述层级、锚点和修复次数；
- `stateUpdate`：服务端固定的访谈状态更新；
- `meta.depthReached`：当前已覆盖深度。

用户界面最终只呈现 `thinkingSummary` 和 `question`。

## 七、流式与非流式路径

### 7.1 非流式路径

非流式接口等待模型完整返回，然后一次性：

1. 解析标记；
2. 组装 Assistant Turn；
3. 经过节点九检查；
4. 持久化并返回完整会话结果。

### 7.2 流式路径

流式接口通过 SSE 向前端发送三类阶段状态：

1. `thinking`
2. `summary`
3. `question`

以及两类增量文本：

- `delta.target=summary`
- `delta.target=question`

模型流式文本先经过标记解析器拆分。服务层会等待问题片段开始后，对已积累的摘要做一次规范化，再把摘要发送给前端。

当前问题输出统一采用缓冲策略：模型分片先在服务端累计，等节点九完成问题协议、重复保护、维度专项检查和 fallback 后，再发送最终问题。摘要也会在发送前完成规范化。

浏览器关闭连接时，AbortSignal 会传递给服务层和 Provider，终止仍在执行的调用，并把已接收的用户提交标记为 `canceled`。流式开始后会先发送确认原话已持久化的 `turn`，完成后再发送最终 `session`。

## 八、失败与 fallback 路径

### 8.1 Provider 配置不可用

系统记录一条 `generate` 阶段失败日志，错误码包含具体配置原因，例如模型、密钥或 Base URL 问题，然后进入确定性 fallback。

### 8.2 Provider 调用报错或超时

- 普通请求：记录失败并进入 fallback；
- 流式请求：先尝试同一 Provider 的非流式调用；
- 第二次调用仍失败：进入确定性 fallback；
- 用户主动取消：异常继续向上传递，终止本轮处理。

### 8.3 模型返回空内容

系统记录 `QUESTION_EMPTY_OUTPUT`，随后进入 fallback。

### 8.4 输出缺少标记

整段文本被视为问题，摘要由后续服务端摘要逻辑补充。该路径仍被视为一次成功的模型输出。

### 8.5 确定性 fallback

系统根据以下材料直接生成一个模板问题：

- 当前维度；
- 当前阶段；
- 最新事件档案；
- 本轮 `questionSpec`；
- 当前动作属于普通推进或继续深聊。

fallback 初始摘要为空。服务层随后根据维度语义解释生成一条 `thinkingSummary`，并继续交给节点九检查。因此，模型服务异常时，访谈仍能继续推进。

### 8.6 可观测记录

每次模型尝试都会写入 AI 请求记录：

- 会话 ID；
- 阶段：`extract` 或 `generate`；
- Provider；
- 成功状态；
- 延迟；
- 错误码。

## 九、结构化抽取调用与本节点的关系

为了准确理解一次完整回复的模型使用，需要区分两条调用。

### 9.1 槽位抽取调用

- 调用时机：意图层允许抽取时；
- 输出：维度字段 JSON；
- 调用方式：非流式 `complete`；
- 参数：`temperature=0.15`、`maxTokens=500`；
- 校验：对应维度的 Zod Schema；
- 尝试次数：最多两次；
- 失败结果：采用保守规则抽取；
- 成功结果：AI 抽取优先，规则结果补充空字段。

### 9.2 对话生成调用

- 调用时机：动作层决定继续追问；
- 输出：带标记的摘要和问题文本；
- 调用方式：支持流式和非流式；
- 参数：`temperature=0.45`、`maxTokens=500`；
- 失败结果：根据问题规格生成确定性问题。

这两次调用共享当前会话材料，同时拥有独立 Prompt、独立输出协议和独立失败回退。

## 十、五个维度的共用机制与差异

### 10.1 共用机制

五个维度共用：

- Provider 选择与调用接口；
- `temperature=0.45` 和 `maxTokens=500`；
- `<<SUMMARY>>`、`<<QUESTION>>` 输出协议；
- 同一个流式解析器；
- 180 字摘要和 160 字问题长度限制；
- `questionSpec` 优先、模型候选问题随后接受表层协议处理的机制；
- Provider 失败后的确定性 fallback；
- AI 请求日志。

### 10.2 维度差异

差异主要通过 Prompt、事件档案字段和问题规格进入模型：

| 维度 | 模型生成时重点 |
|---|---|
| 开心 | 具体开心点、状态变化、意义型或轻快乐线索 |
| 充实 | 真实推进/积累/贡献证据，再进入值得感标准 |
| 思考 | 具体触发、新理解、视角变化或判断依据 |
| 改进 | 好状态的重复条件或坏状态的卡点，再进入可控小调整 |
| 感谢 | 对方具体行动、被回应的需要、感谢原因和关系线索 |

五个维度的流式问题都会完整缓冲后再展示；充实、思考和感谢的专项保护继续发生在节点九。

## 十一、当前设计中存在的问题

### 11.1 一次正常回复通常触发两次模型调用

槽位抽取和追问生成分别请求模型。两次调用提升了语义处理能力，同时增加了整轮等待时间、调用成本和两次理解口径产生偏差的可能性。

### 11.2 摘要与问题依赖文本标记协议

对话生成采用 `<<SUMMARY>>` 和 `<<QUESTION>>` 分段。标记缺失时，系统会把整段内容归入问题，摘要由服务端补充。模型遵循格式的稳定性会直接影响展示结构。

### 11.3 有效输出门槛较宽

只要摘要或问题任一项存在内容，本次调用就被记录为成功。只有摘要、问题为空的情况会进入完整 fallback；部分缺失依赖后续服务端补齐。

### 11.4 请求级故障切换范围有限

流式失败会切换为同一 Provider 的非流式调用。当前请求运行过程中，上游 Provider 持续异常时会进入规则 fallback，跨 Provider 切换只发生在配置解析层的数据库配置与环境兜底之间。

### 11.5 问题统一缓冲会影响首字速度

所有正常追问都会先完成服务端检查，再展示最终问题。这提高了可见文本与落库文本的一致性，也让问题首字速度包含完整生成与检查耗时。

### 11.6 流式体验主要来自最终文本分块

模型候选分片留在服务端内部。节点九完成检查后，最终摘要和问题再分块到达前端，因此用户看到的是经过收敛的最终文本，模型实时生成感会相对减弱。

### 11.7 五维差异主要集中在一份大型 Prompt 中

五个维度共用生成管线，维度差异由多组条件化规则注入。同一输出协议下承载的约束较多，模型对不同维度规则的执行稳定性依赖 Prompt 遵循能力。

---

## 十二、产品级概括

模型生成层可以概括为：

> **接收已经确定的访谈任务，通过当前可用的大模型生成“理解摘要＋一个追问”，再将文本交回服务端协议进行收口。模型负责语义和措辞，服务端负责流程权限、问题目标、失败兜底和最终可用性。**
