# 节点九：服务端检查与输出控制

> 事实口径：本文依据 2026-07-20 工作区当前代码核对，面向非技术背景 AI 产品经理。

## 核心结论

服务端检查与输出控制层承担“发布前编辑部”的角色。模型生成摘要和问题后，服务端会拆分内容、控制长度、检查问题是否清楚、处理重复追问、执行维度专项保护、补齐空内容、重写不合格摘要，并强制写入服务器认可的回合状态。最终，系统只把浅色思路摘要和一个正式问题投影到对话界面。

这一层同时管理两种输出方式：

- 普通 JSON：全部处理完成后一次返回。
- SSE 流式输出：先确认用户原话已经被服务端接收，再按“思考中 → 摘要 → 问题 → 最终会话”逐步发送。

模型输出无法直接决定完成、转向或选择卡状态。这些状态由动作决策层先行确定，服务端在正常追问回合中再次固定为当前允许的状态。

## 1. 为什么存在

模型生成具有语言弹性，产品协议要求稳定：一轮只有一个问题、问题围绕当前事件、摘要承担理解说明、用户边界优先、已否认方向得到保护、页面刷新后状态一致。

因此，这一层解决五类发布风险：

1. **格式风险**：模型可能漏掉分段标记、输出过长或只生成一部分内容。
2. **表达风险**：问题可能抽象、包含多个认知任务、缺少具体锚点或使用内部理论词。
3. **对话风险**：继续深挖时可能重复上一问，重新追问用户已经否认的方向。
4. **控制风险**：语言模型输出的状态字段可能影响产品分支。
5. **传输风险**：流式文本需要与最终保存结果保持尽量一致，错误也需要以统一协议返回。

## 2. 输入

本层接收三类输入。

### 2.1 模型候选内容

模型当前只生成两段用户可读内容：

- `thinkingSummary`：浅色思路摘要
- `question`：正式追问

模型使用 `<<SUMMARY>>` 和 `<<QUESTION>>` 分隔两段内容；历史 `<<INSIGHT>>` 标记也会按摘要处理。

### 2.2 服务器访谈上下文

- 当前维度和阶段
- 最新事件档案
- 本轮 `questionSpec`
- 最近历史问题
- 当前动作：正常回复或继续深挖
- 用户是否否认过某个场景、需要或关系解释

### 2.3 服务端预设回合

选择卡、边界收束和确定性问题修复在上游已经形成完整 `assistantTurn`。这类回合直接进入可见内容投影和保存流程。模型调用失败时产生的确定性 fallback 追问仍会经过正常追问的最终整理流程。

## 3. 检查顺序

当前正常模型追问的实际顺序如下。

### 第一步：分段解析

流式解析器识别摘要和问题标记，并在标记跨多个数据块时暂存不完整标记。

- `<<SUMMARY>>`、`<<INSIGHT>>` → 摘要
- `<<QUESTION>>` → 问题
- 整段文本未识别到标记 → 全部按问题处理

解析完成后，摘要最多保留 180 个字符，问题最多保留 160 个字符。

### 第二步：形成服务端回合结构

服务端把两段文本装入 `assistantTurn`，并自行生成：

- 内部 `analysis`
- `questionSpec`
- `stateUpdate`
- 已覆盖深度 `meta.depthReached`

这里的 `analysis` 是服务端模板化描述，来源于当前维度、阶段和动作。它不承载模型的隐藏推理过程。

### 第三步：问题表达协议

服务端先依据 `questionSpec` 处理问题。

对于直接反应、原因证据和判断线索三类目标，当前代码优先使用服务端的结构化问法表达器。模型候选问题通常会被服务端问法替换。事件锚点和先前判断类目标会更多保留候选问题，再进入统一可理解性检查。

问题质量门当前检查：

- 内部理论词
- 跨类别比较
- 多跳推理
- 一问包含多个认知动作
- 抽象开场
- 与事件锚点连接较弱
- 难以用一个具体例子回答
- 思考维度缺少具体锚点

检查通过后保留当前问题。检查未通过时，系统根据原因执行一次降级，例如：

- 使用用户原有词语
- 收窄成一个认知动作
- 加入具体事件锚点
- 改成“先举一个例子”

降级版本还会再检查一次。第二次仍未通过时，系统使用最保守的 `event_anchor + concrete_anchor` 问题作为最终问题。

### 第四步：继续深挖保护

这一组检查只在 `continue_current_event` 场景运行，顺序为：

1. **思考维度场景否认保护**：历史中已经问过具体经历或对话，用户明确否认后，新问题再次触碰同类场景时，服务端改问具体顾虑、画面或念头。
2. **感谢维度否认保护**：新问题碰到已经否认的需要、感谢原因或关系假设时，服务端回到“对方具体帮到你的哪一下”。
3. **最近问题重复检查**：与最近四个 AI 问题语义等价时，服务端生成当前阶段的替代问题；思考维度优先使用具体锚点问题。

重复判断会清理空格、标点和常见问题框架，例如“如果只留一点”“换句话说”。因此，增加一个轻微前缀通常仍会被视为重复。

### 第五步：充实维度专项检查

充实维度在所有正常模型追问中都会执行专项检查，覆盖正常回复和继续深挖。它检查：

- 问题目标与当前缺口是否匹配
- 是否重复询问已经覆盖的进展证据或值得感标准
- 措辞是否自然
- 进展问题是否过于抽象

命中后，服务端重新判断当前应补“进展证据”还是“值得感标准”，再生成对应替代问题和新的问题规格。

### 第六步：空内容兜底

如果最终问题为空，系统根据当前维度、阶段和问题规格生成确定性问题。

如果摘要为空，系统按以下顺序补齐：

1. 使用已有 `insight`
2. 使用服务端维度语义解释生成摘要

模型服务不可用、流式调用失败或返回空内容时，AI 服务会直接创建确定性 fallback 回合，再进入同一套最终整理。

### 第七步：思路摘要检查与重写

服务端对 `thinkingSummary` 单独检查。当前会触发重写的情况包括：

- 写成问句
- 出现“下一步、追问、确认”等系统操作口吻
- 使用未来源于用户原话的“我想……”表达
- 写成内部理论解释
- 基本只是复述用户原话，缺少维度语义上的提升

符合要求的摘要最多保留 180 个字符。触发重写时，服务端依据同一份维度语义解释，重新生成自然的浅色思路摘要。

### 第八步：强制回合状态

正常追问完成后，服务端统一覆盖回合控制字段：

- `turnPhase`：开场或深挖
- `shouldEndDimension`：`false`
- `offerChoice`：`false`
- `choiceKind`：`null`
- `choiceReason`：空字符串

继续深挖固定进入 `digging`。选择卡和转向已经由动作决策层提前创建，因此正常模型追问始终保持在访谈状态。

### 第九步：可见内容投影

界面显示规则是：

- 有正式问题：显示 `thinkingSummary`，随后显示 `question`
- 摘要为空且有历史 `insight`：用 `insight` 作为摘要
- 当前回合问题为空：可单独显示 `insight`

`analysis`、`questionSpec`、`stateUpdate` 和 `meta` 继续作为内部回合数据，展示辅助函数只输出摘要、问题或独立说明。

## 4. 修正、替换与兜底逻辑

当前处理可以分成四档。

| 处理档位 | 触发条件 | 结果 |
|---|---|---|
| 规范化 | 内容基本可用 | 拆分、去首尾空白、限制长度、补齐结构 |
| 修正 | 摘要语气或问题表达存在局部风险 | 改写摘要，或降低问题抽象程度 |
| 替换 | 问题重复、目标错位、触碰否认方向 | 使用服务器确定性问题和更新后的 `questionSpec` |
| 兜底 | 模型不可用、输出为空、两轮质量门均未通过 | 使用当前维度和阶段的保守问题，并生成服务端摘要 |

问题被替换后，原模型问题不进入最终保存的 `assistantTurn`。摘要被重写后，保存和最终响应都使用重写后的版本。

## 5. 输出协议

### 5.1 普通 JSON 输出

普通接口在全部处理和保存完成后返回：

- 用户可读的 `assistantMessage`
- 完整内部 `assistantTurn`
- 会话状态、轮数、事件档案和可生成日志状态
- 更新后的完整 `session`

响应还会经过 Schema 校验。结构异常会转成统一的访谈错误。

### 5.2 SSE 流式输出

流式接口使用五类事件：

| SSE 事件 | 内容 |
|---|---|
| `turn` | 服务端已建立的用户提交记录；确认原话已经持久化，并返回 `clientTurnId / status / attemptCount` |
| `phase` | `thinking / summary / question` 阶段变化 |
| `delta` | `summary` 或 `question` 的文本增量 |
| `session` | 保存完成后的最终会话 |
| `error` | 流内发生的结构化错误 |

关键控制规则：

- `turn` 在 AI 处理开始前发送。页面收到后清除输入草稿，并把本轮标记为已被服务端接收。
- 摘要增量会先暂存，在问题开始输出时完成规范化，并且只向前端发送一次完整规范化摘要。
- 当前问题文本统一等待服务端检查完成，再按最终版本分块发送。用户看到的问题与最终保存的问题保持一致。
- 保存完成后发送 `session` 事件，它承担本轮成功完成的最终状态确认。
- 浏览器取消请求时，服务端中止模型调用，把已接收的用户提交标记为 `canceled`，并保留用户原话供后续继续生成。

选择卡、问题修复和暂停会话提示等服务端预设回合，会跳过模型流，直接按摘要和问题分块输出。

### 5.3 错误协议

普通接口和流式接口共用结构化错误 `issue`：

- `code`
- `title`
- `message`
- `resolution`
- `retryable`
- `action`
- `requestId`

请求格式、内容过长、登录失效、会话失效、选择过期、本轮仍在处理、对话位置过期、待恢复提交失效、数据库写入失败和响应 Schema 异常都映射为明确错误码。

错误详情、数据库类型、原始异常和服务商信息记录在服务端日志中；用户收到面向操作的说明和 `requestId`。流建立前的错误使用 JSON 和 HTTP 状态码；流建立后的错误使用 `error` SSE 事件。

## 6. 五维共用与专属保护

| 维度 | 共用检查 | 当前专属保护 |
|---|---|---|
| 开心 | 分段、长度、问题质量门、摘要重写、空内容兜底、状态强制 | 主要依赖共用协议和开心维度语义摘要 |
| 充实 | 全部共用检查 | 目标错位、抽象进展问题、自然度和语义重复检查；流式问题全量缓冲 |
| 思考 | 全部共用检查 | 质量门要求更多具体锚点；继续深挖时防止回到已否认的具体经历或对话；重复后优先落到顾虑、画面或念头 |
| 改进 | 分段、长度、问题质量门、摘要重写、空内容兜底、状态强制 | 主要依赖共用协议和改进维度语义摘要 |
| 感谢 | 全部共用检查 | 继续深挖时读取 `deniedTargets / deniedHypotheses`，避免重复验证已否认的需要和关系解释 |

五个维度的 `thinkingSummary` 都使用同一层维度语义解释进行重写，因此重写结果会体现各维度不同的产品目标。

## 7. 用户可见与内部信息边界

用户在对话区实际看到：

- 浅色思路摘要
- 一个正式问题
- 服务端预设的说明或选择卡
- 结构化错误说明和处理建议

内部回合数据包括：

- 服务端 `analysis`
- `questionSpec`
- `stateUpdate`
- `meta.depthReached`
- 事件档案、证据状态和进度判断
- 原始异常与服务商错误

当前边界主要由前端展示逻辑实现。API 响应仍包含完整 `assistantTurn`、`snapshotData` 和 `session`，对话展示辅助函数只投影用户可读部分；原始异常和数据库细节保持在服务端日志中。

## 8. 当前问题

### 8.1 检查规则分布在多个文件和阶段

分段解析、问题质量门、继续深挖 guard、充实 guard、摘要重写、流式缓冲和错误协议分别位于 AI 服务、问题协议、访谈服务和 API 路由中。理解最终一句问题的来源需要追踪多次转换。

### 8.2 通用重复保护集中在“继续深挖”

最近四问的通用语义重复检查只在 `continue_current_event` 执行。正常回复场景中，充实维度拥有专项重复检查；开心、思考、改进和感谢主要依赖问题规划、Prompt 和可理解性协议降低重复概率。

### 8.3 问题质量门主要采用固定语言模式

内部理论词、抽象表达、多认知动作和例子可回答性主要通过固定词语与句式识别。语义等价的新表达可能绕过检查，正常自然表达也可能触发降级。

### 8.4 摘要重写采用整段替换

摘要中一处触发系统口吻、问句或理论表达时，服务端会用维度语义解释重建整段摘要。原摘要中自然且有价值的表达也会一起被替换。

### 8.5 问题统一缓冲后再展示

当前问题文本会等待问题质量门、重复保护和维度专项检查完成后再展示。这一设计保证用户看到的追问与最终落库版本一致，同时减少了模型逐字生成的即时感。用户仍会先看到“思考中”和随后分块出现的最终摘要、问题。

### 8.6 流式成功依赖 `session` 事件确认

当前 SSE 协议把 `turn` 作为“用户原话已被接收”的确认，把 `session` 作为“AI 回应和会话状态已完整保存”的确认。两者之间发生失败或取消时，用户原话仍在服务端，页面会恢复 `pendingUserTurn` 并提供“继续生成”。

### 8.7 内部信息边界属于展示层边界

页面只渲染摘要和问题，API 仍向已登录客户端返回完整回合结构和事件档案。普通用户界面保持简洁，同时浏览器网络层可以读取这些内部字段。

### 8.8 模型降级对用户保持静默

服务商不可用、流式失败或空输出时，系统使用确定性问题继续访谈，异常只进入 AI 请求日志。用户可以继续使用产品，但很难从当前体验判断这一轮采用了模型表达还是 fallback 表达。
