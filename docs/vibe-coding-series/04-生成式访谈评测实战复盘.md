# 一次生成式访谈评测，为什么从 8 张校准卡一直走到 v8r2

2026 年 8 月，Daily Light 的生成式访谈进入了一段很密集的评测与调优。

这段经历从 8 张人工校准卡开始，经历了临时 Prompt 的真实输出、本机直连网页、Prompt 与 Interview Skill 的职责重组、Thinking 能力探针、共同任务结构、私有 Preview 评测运行器，以及 GI-088 v0 到 v8r2 的多轮候选。

过程里踩到的坑很具体。网页曾经没有真正连上 DeepSeek，API Key 在用户点击发送后才报错，旧 AI 的问题被混进新候选的上下文，一个程序保护把用户卡在无法继续的页面里，1600 个 Token 又让 high 模式连续三次把预算全部用在推理上。还有一次，为了保证“单轮一问”，程序直接数问号。两个语气连贯、只需要用户回答一件事的问句，也会被拦下。

这些问题最后促成了一套更可用的工作方式。评测需要从干净的用户起点开始，候选只改一个主要影响因素，产品质量和工程可靠性分开记录，程序只执行可以客观确定的边界，真人体验拥有最终产品裁决权。

这篇复盘记录了这套方法是怎样被错误一步步逼出来的。

## 一、复盘范围与当前结论

本文覆盖从板块 6 首批人工校准到 GI-088 v8r1 最终 12 项真人验收起点的完整过程。文末当前交接已同步到 v8r1 A1 事故与 v8r2 底座加固；评测数据、人工判断、Codex 初评、工程故障和历史候选的身份分开保存。

截至 2026 年 8 月 10 日，已确认事实如下。

- GI-068 到 GI-080 继续关闭，AI 产品工作方法 v1.0 继续冻结。
- 板块 6 继续进行中，板块 7 正式接入与板块 8 继续等待。
- Production 继续使用 `legacy + baseline`。本轮候选只在私有 Preview 运行。
- GI-088 v8 的 A1 真人轨迹已通过，10 次 Provider 调用全部首次返回有效结果。
- GI-088 v8r1 修正了礼貌停聊的多余调用；随后 A1 真人轨迹暴露了“事件内容中的负担表达被程序误判为停聊”的单例阻断，该 run 退出最终准入候选。
- 当前 v8r2 正在统一加固控制意图、调用事务、人工复核和评测工作台。主体实现与核心零模型回归已通过，八项 Preview 开门审计差额、最终静态门、Preview 和新 `0/12` run 继续执行。

## 三、实操中最关键的坑

### 1. 任务未达到退出条件，会话却提前收口

板块 6 开始时，用户要求先复述目标、冻结输入、评测资产、开放问题、依赖和退出条件，然后每次聚焦一个产品选择。会话一度直接退出了计划讨论，当时板块 6 依然缺少真人校准、正式判尺和可交给板块 7 的资产。

这次问题反映出一个协作缺口。“一次回答已经完成”和“产品阶段已经完成”需要两套判断。随后把每轮停止点写入计划，并在文档里保持板块状态。完成 8 张校准卡只是第一个真人校准节点，它不代表板块 6 结束。

可复用的经验是让每个任务同时具备两个终点。当前工作的停止点告诉 AI 何时暂停，阶段退出条件告诉项目何时可以向下游交付。

### 2. 用一份证据同时回答了太多问题

8 张人工卡能够帮助产品负责人和 Codex 校准“什么程度算轻微问题”和“什么程度算单例阻断”。这些卡片里的 AI 回应由人工编写，所以它们只能校准判断标准。

GI-081 又试图用六题同时比较一次调用与两阶段调用。两套候选使用了同一个 DeepSeek 模型，可是共享 Prompt 已经写入模式任务、优先级、动作定义、提问价值和证据约束。这些内容本来属于尚未讨论清楚的板块 7 产品策略。

当一份证据同时改动 Prompt、Skill、上下文和调用结构时，评测结果很难回答具体哪个因素起了作用。GI-081 最终保留了真实失败，证据身份调整为“临时 Prompt 下的诊断基线”。这个调整保住了历史，也防止它替代正式架构裁决。

从此，每份证据都要先说清一件事。它用来校准判尺、发现失败、比较候选、验证稳定性，还是承担发布准入。一份证据可以有多个用途，每个用途都需要独立的资格说明。

### 3. 新 AI 在收拾旧 AI 留下的问题

GI-087 的一条校准输入里，用户可见上下文包含旧 AI 的追问。例如“你心里最直接的感受是爽还是轻松”，这个问题已经把用户推向了二选一。新候选后续的表现，很大一部分是它能不能修复旧问题。

这会使评测对象发生偏移。产品关心新候选从用户第一句开始会怎样理解和追问。用带着旧 AI 干预的中段输入去评价新候选，最后很难判断是新候选本身的问题，还是起点已经被改写。

这次审计形成了三条硬约束。

- 每条完整轨迹从固定 A0 和用户真实 U1 开始。
- 同一条轨迹里只使用同一候选生成的 AI 回合。
- 历史中段片段继续可以用于失败分析，证据标签需要明确写成条件检查或历史证据。

输入血缘因此成为评分前的第一项检查。上下文资格不成立时，分数再精细也无法支持当前候选的结论。

### 4. 规则越写越多，模型仍然没有做出正确选择

GI-084 的早期候选把很多已冻结规则写进 Prompt 和 Interview Skill。结构合法率确实改善了。到 v0.3 时，8 次调用已经能够全部通过结构检查，两个秋招关键决策点仍只有 2/4 达到产品要求。

这里的问题发生在语义选择上。模型知道需要保留长期方向和当前 offer，后续还是会把“先拿 offer”写成用户已经放下长期方向。GI-085 把这个漂移定位为 `focus → openPart → visible`。共同问题在进入本轮探查时缩成了单一方面，最后可见回应又把临时入口写成用户决策。

修正随后转向任务结构。`workingTask` 保存整段聊天正在共同弄清的问题，`nextInquiry` 只保存用户本轮需要回答的一项内容，以及这个回答会如何更新共同问题。模型可以临时选择入口，相关整体仍然保留。

这次经历确定了冻结规则的分流方法。

- 跨场景的判断方法进入 Prompt 或 Interview Skill。
- 可以由客观事实稳定判断的边界交给程序。
- 具体表达和长尾场景进入开发评测集。
- 严重安全、隐私、越权和用户控制问题才可以直接形成硬失败。

规则的价值来自清楚的职责和重要的决策。它的数量本身无法保证模型理解用户。

### 5. 程序保护把主观体验简化成字符计数

“程序保护”原本的用途是防止一些可以客观确定的失控。例如一次用户提交只能触发一次首次请求，来源引用只能指向用户原话，已结束轨迹不能再产生请求。

它在评测里一度扩张到了提问质量。程序通过统计中英文问号，确保用户可见内容只出现一个问题。一条回应同时出现“你当时更在意什么？还是更担心会失去什么？”，程序会认为它有两个问题。用户实际上只需要围绕同一个焦点回答。

更严重的问题出现在页面上。程序拦下结果后，用户既不能继续输入，也不能自然收口，只能看到“本轮触发程序保护”。这个保护避免了一条不合同的回应进入正式对话，同时制造了一个用户无法退出的终态。

v6 将评判单位改成“一个独立回答任务”。一轮可以有两三个连贯的问句，只要用户能围绕同一件事回答。产品负责人对 11 个可见提问完成人工分类，其中 9 个同焦点且自然，2 个同焦点但稍重，独立回答任务为 0。

v8r1 又补了一个更关键的反例。用户在讲述事件时表示向家人解释很累，旧意图规则只看到“累”，将它记为 `fatigue_feedback + stop_follow_up`。GI-088 再把这个结果升级为停止当前访谈，最终覆盖了已经生成的有效模型回应。产品负责人将这条轨迹判为体验变差和单例阻断，v8r1 因此退出最终通过候选。

这条证据推动 v8r2 将控制决策收紧到可核查的条件。程序只执行用户本人、肯定表达、指向当前访谈或问题、并且仍然有效的明确控制命令。事件内的疲惫、烦躁、停止行为和第三方表达继续作为访谈内容。证据不足时继续访谈，并将程序介入保留给人工复核。

这次修正给出了程序保护的边界。程序要保证可计算的安全事实，提问是否让人愿意继续，交给模型原则、开发评测集和真人体验来裁决。

### 6. 把手动重试当成通用修复按钮

GI-088 v0 的 A2 high 在同一轮经历了首次调用和两次手动重试。三次请求使用同一份上下文、Prompt、Skill、模型和 1600 Token 输出上限。三次都在 `finishReason=length` 结束，`completionTokens` 和 `reasoningTokens` 都等于 1600，可见回答为空。

这个结果说明重试能不能帮忙，取决于失败是否具有偶发性。网络抖动、上游短暂失败和健康生成被本地超时截断，可以进入有限的技术恢复。稳定的输出预算不足、固定的结构合同冲突和内容质量问题，再次发送通常只会增加调用和用户等待。

v1 去掉了这条评测候选的应用层 Token 上限。v2 开始分别记录响应头、首个正文片段、正文空闲时间和总时间。v4 又证明历史的 30 秒总截止会在上游已经返回响应头后，于 30.002 到 30.003 秒中断正常的 high 正文。

恢复策略随后使用共享总期限，首次失败和一次自动恢复共用 90 秒。每段用户原话保留明确调用上限，失败证据继续保存，页面再把最终决定交还用户。

### 7. 评测网页自己没有通过端到端预检

评测运行器初期出现过一组本可以在用户开始前发现的问题。DeepSeek 凭据缺失，本机页面一度只有聊天外壳，Vercel 构建漏掉独立 Prisma 运行文件，Preview 登录名单和评测名单又有不一致的风险。

这些失败对模型质量没有判断价值，它们会直接打断产品负责人的真人体验。尤其当网页已经告诉用户“可以开始”时，第一次提交才发现凭据或 Provider 不可用，会使后面的评测说明失去信任。

建设验收随后拆成了四层。

1. 静态检查确认 Prompt、Skill、结构、数据集和指纹一致。
2. 假 Provider 走完开始、提交、刷新恢复、手动恢复、评价和封存。
3. 私有 Preview 检查登录、独立数据库、页面读回和 Production 404。
4. 每种模型配置先做一次单独授权的技术冒烟，正式批次使用新的授权和执行指纹。

运行器可以打开、页面可以登录和用户可以完成一整条轨迹，是三个不同的验收层次。它们需要逐层读回。

### 8. 一条长会话承担了过多职责

当前对话经历了产品规则讨论、候选设计、文档写回、代码实现、模型调用、真人裁决、故障排查、下一版开发和再部署。每次用户发现新问题，会话都继续向后叠加上下文。

长上下文带来了三类实际问题。第一类是名称漂移，同一时期存在 GI-083 的 Skill 、用户在新窗口打包的 Board 7B Skill，以及后来的 GI-084 Skill。用户需要反问“你调整的是哪个 Prompt 和 Skill”。第二类是工作性质混合，运行结果一出现，同一条会话立即进入归因和修复，容易在证据未封存时改动候选。第三类是旧计划与新计划并存，新会话需要花很长时间猜当前执行入口。

用户最终确认了一个更符合真实工作的会话机制。

` 建设评测运行器 → 真人完成一批评测 → 批次迭代会话 → 下一候选就绪 → 真人完成下一批评测 `

一套运行器的计划、开发、测试和 Preview 部署可以在同一条建设会话里完成。产品负责人通过网页完成整批评测时，Codex 会话关闭。整批结果封存后，再开一条批次迭代会话，在其中完成全量复盘、产品讨论、下一个主要影响因素选择、候选开发和静态验证。

会话因此围绕可以独立验收的真实节点切分。计划模式与执行模式的切换，以及一次修改多个代码文件，都可以留在同一条会话里。当一批新结果已经封存、产品规则重新打开、工作转入正式评测资产、进入板块 8，或出现独立工程故障时，再开新会话。

## 四、为什么“评测包”不再作为对外主术语

过程中曾反复使用“评测包”。这个词可以指六题数据，也可以指 Prompt、运行脚本、Trace 和报告模板的合集。不同会话对它的理解不一致，产品负责人无法从词本身判断当前缺的是数据、工具、标准还是结果。

统一术语直接按业务职责命名。

| 统一术语 | 它回答的问题 | 本项目里的实例 |
| --- | --- | --- |
| 评测方案 | 评什么、怎样评、谁裁决、何时停止 | 九类判尺、单例阻断、人机分工和通过门 |
| 开发评测集 | 用哪些任务发现候选问题 | 8 张校准卡、12 项真人交互任务 |
| 试次 | 哪个候选在哪个输入和配置下产生了什么 | 一条用户提交对应的 Provider 请求与结果 |
| Trace | 这个结果怎样得到，问题发生在哪一层 | 语义动作、来源、状态变化、调用血缘和安全诊断 |
| 评测运行器 | 怎样稳定执行任务、保存进度和防止证据污染 | 私有 Preview 工作台、独立评测库、幂等与封存 |
| 评测报告 | 整批结果说明了什么，还有什么未知 | 产品负责人裁决、Codex 九类初评、技术总账和下一候选建议 |

这些内容合在一起，构成 AI 产品经理需要建设的评测体系。“测试机、验证机、评测机”可以理解为不同环境或执行阶段的口语表达。在本项目里，更有用的说法是讲清评测方案、开发评测集、运行器、Trace 和报告分别承担什么。

## 五、一套更可用的协作机制

### 建设会话

建设会话只承担一个已确认候选的实现、自动测试、Preview 部署和零调用读回。计划和开发可以连续完成，因为它们服务同一个可验收结果。

这条会话需要带着一张简短交接卡开始。

- 唯一目标与停止点。
- 当前板块和候选版本。
- 冻结的 Prompt、Skill、模型、上下文、任务结构与评测口径。
- 本轮允许修改的主要影响因素。
- 允许操作和保持不变的 Production 范围。
- 上一批已封存证据、调用数与当前开放问题。

运行器完成后，这条会话停在可使用的评测网址和空白批次读回。

### 真人评测期间

产品负责人在网页独立完成整批任务。Codex 不进入对话过程，也不在中途修改 Prompt 或判尺。评测库保存进度、完整对话、Trace、产品判断、技术失败、恢复和候选指纹。

这个阶段可以因为一次真实故障开启短故障会话。修复若改变候选、上下文或执行指纹，已有结果按影响范围重新确认资格。

### 批次迭代会话

整批结果封存后，新开一条批次迭代会话。这条会话连续完成下列工作。

1. Codex 对整批结果做独立九类初评。
2. 产品负责人与 Codex 一起查看完整证据，保留两份判断的差异。
3. 将所有问题按共享原因归组，再根据用户伤害、发生频率和恢复难度排序。
4. 选择下一版唯一主要影响因素。其他问题进入队列，它们继续在同一条会话里被讨论。
5. 完成下一候选的产品设计、实现、定向测试、静态验证和新指纹。

这条会话在“下一候选已经就绪，等待下一批真人评测”时结束。

## 六、一批结果怎样复盘

这段实操最后形成了一个稳定的复盘顺序。

### 第一步先冻结原始证据

对话、模型最终可见输出、语义结构、程序保护、调用参数、耗时、Token、恢复血缘和用户评价一起封存。新候选从新版本开始，不回写原始结果。

### 第二步检查证据资格

- 输入是否从干净 A0 与 U1 开始。
- 整条轨迹是否使用同一候选。
- 任务提示是否只对评测人可见。
- Prompt、Skill、模型、上下文、程序和数据集指纹是否一致。
- 工程修复是否改变了候选资格。

### 第三步分开三本账

| 账目 | 主要记录 | 主要裁决者 |
| --- | --- | --- |
| 产品体验 | 用户感受、任务是否触发、回应是否可用、问题是否愿意回答 | 产品负责人 |
| 模型质量 | 九类判尺、来源、焦点、下一步价值、认识、负担、表达与状态 | Codex 独立初评，产品负责人最终裁决 |
| 工程可靠性 | 请求数、首次成功、超时、空内容、程序保护、恢复、重复消息与封存 | 自动检查与工程审计 |

三本账可以同时出现不同结论。一条回应内容可以很好，但程序保护阻止了它进入对话。一条轨迹最后可以完成，但经历多次恢复以后用户体验仍然不合格。分开记录才能找到应该修改的层次。

### 第四步用九类判尺定位模型问题

当前九类判尺来自 GI-074 并在板块 6 校准过程中继续调整。

1. 任务与模式。
2. 焦点与上下文。
3. 来源忠实。
4. 下一步价值。
5. 认识或结果。
6. 回答负担与节奏。
7. 用户控制与安全。
8. 用户可见表达。
9. 状态与成果收口。

每类使用 `2 / 1 / 0 / N/A`，分数需要引用用户可见证据。它们用来定位问题，整体体验判断仍然保留。产品负责人的先验与 Codex 初评分开写，可以避免后者提前影响前者。

### 第五步追到可修改的主要原因

这一步先问问题属于哪个影响因素。

- 用户任务或成功标准。
- 输入与上下文。
- 基础 Prompt 或 Interview Skill。
- 任务结构与模型输出合同。
- 模型、Thinking 与 Provider。
- 程序状态、保护与恢复。
- 评测运行器和页面交互。
- 评测口径与人工裁决。

同一批可以讨论所有问题，下一候选只选择一个主要影响因素。它能使新结果有较清楚的归因。当几个修正共用同一个原因且无法独立生效时，需要在候选说明里写清共同依赖。

## 七、这段过程做对了什么

复盘踩坑时，也要保留已经建立的好习惯。

### 失败证据一直被保留

GI-081 的临时 Prompt、GI-083 v0 的事实卡、GI-084 到 GI-086 的 No-Go、GI-087 的污染上下文、v0 的 1600 Token 失败、v7r1 的 Prefix 兼容失败、v7r2 的 Ark Flash 可靠性结果和 v8r1 A1 的控制误停都保留在版本化资产中。它们继续提供回归和归因证据，当前执行入口指向 v8r2 底座加固任务。

### 授权和运行指纹经过了逐步收紧

后期候选都会绑定模型、Prompt、Skill、数据集、运行参数和服务版本。新指纹使旧授权自动失效，技术冒烟和正式批次分别授权。这个设计保护了证据的版本身份。

### 产品裁决与 Codex 初评分开保存

产品负责人先根据完整体验给出 `better / same / worse` 与质量等级，Codex 在整批封存后再做九类初评。两份判断可以不一致。这种不一致能够暴露判尺歧义，不需要被平均分掩盖。

### 项目能够在证据足够时提前停止

v3 在 A1 已经暴露共同阻断后，没有继续消耗 A2 和 A3。v6 在产品负责人确认单一回答焦点通过后，没有继续运行剩余两项。v7r1 的 Prefix 合成兼容探针在生成前已确认 API 不兼容，候选停在 Preview 之前。这些停止避免了无法带来新判断的调用。

### 生产边界始终保持清楚

所有候选都在本机或私有 Preview 运行，独立评测库保存原始对话与 Trace。Production 一直保持 `legacy + baseline`。这条边界使真实评测可以深入迭代，同时避免历史候选或未完成判尺进入生产。

## 八、下一批开始前的最小检查

### 评测方案

- 当前批次只回答一个产品问题。
- 开发评测集覆盖关键用户行为和已知失败。
- 通过门、单例阻断、提前停止和整批失败条件已写清。
- 产品负责人、Codex、程序和自动检查的职责已分开。

### 候选与输入

- 当前唯一候选和执行指纹已读回。
- 新候选只改一个主要影响因素，共同依赖已写清。
- 输入从干净 A0 与用户 U1 开始，轨迹中不混用旧 AI 回合。
- 任务指令只对评测人可见，不提前告诉模型期望表现。

### 评测运行器

- Provider 凭据、模型、权限、独立数据库和运行文件在用户开始前已通过。
- 一次用户提交对应一次首次请求，刷新不会重复发送。
- 程序保护、技术失败和用户主动结束都有可达的后续动作。
- 恢复只处理已定义的偶发技术失败，每段用户原话具有明确调用上限。
- 运行器可以封存完整批次，也可以封存有效的提前停止。

### 人工裁决与报告

- 产品负责人先完成整体感受与可用性判断。
- Codex 在批次封存后做独立九类初评。
- 工程可靠性按试次和用户提交分开统计。
- 评测报告保留两份判断、分歧、已确认原因和仍开放假设。
- 下一候选只在全批复盘后建立。
