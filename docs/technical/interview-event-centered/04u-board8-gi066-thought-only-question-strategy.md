## 1. 为什么建立 GI-066

历史方案反复证明，单独把“目标未答完 × 只能由用户提供 × 低负担问题会改变理解”写进 Prompt，无法稳定产生正确的问停和选题：

- `3.29.0` 的 `24` 条工作单轮只有 `3` 条通过，主要失败为认识增量不足、回答负担过高和目标选择偏差；
- v57 简化 Prompt 并注入 Few-shot 后，四角度冒烟达到 `3/4`，想法案例仍把用户已有理解改写成成果；
- v64 R2 的 ask 子集为 `1/4`，v65 两条定向修复为 `0/2`，Prompt 优先级无法稳定执行 GI-039；
- v69/v70 增加 `goal + answerEntry` 后，具体入口仍可能抽象、重复或负担过高；
- 两段式和语义骨架改善了技术职责，第一段继续拥有自由选题和问停权时，语义质量仍不稳定；
- 后续 Preview 又暴露重复问题、纠正后错误结束、浅层完成以及脚本化结果无法替代真人体验。

GI-066 将模糊公式改造成可追踪的判断地图、有限认识动作、系统选题、语义重复门和分层验证。外部四类 Probe 研究提供“具体个案优先、解释式追问后置”的方向；最终规则以本项目历史人工裁决为首要依据。

## 2. 产品目标与完成标准

“理清想法”的基础材料为：

```text
当前判断 + 具体判断依据
```

这两项只构成素材闭环。一次有效 AI 复盘还需要在正式复盘开始后形成至少一项新的认识：

- 判断标准；
- 默认假设；
- 证据张力；
- 取舍条件；
- 判断校准。

认识增量可以来自用户在 AI 提问后形成的新关系、AI 依据至少两侧可靠来源形成的一步安全关系，或用户纠正后实质改变已有成果。初始材料、事实增加、语言重写、重复确认和同义复述均不计为 AI 复盘增量。

用户初始材料已经完整且不存在合格问题时，系统诚实进入开放转场，可以生成日志，但该轨迹不能作为“AI 帮助用户形成新认识”的能力通过证据。

## 3. 判断地图与目标状态

系统为当前事件维护以下目标：

| 目标 | 要回答的问题 |
|---|---|
| 当前判断 | 用户现在怎样理解、判断或选择 |
| 判断依据 | 哪些具体事实支持当前判断 |
| 判断标准 | 用户用什么尺度判断合适与否 |
| 默认假设 | 当前判断依赖什么尚未确认的前提 |
| 证据张力 | 哪些证据支持，哪些证据产生冲突 |
| 取舍条件 | 两项都重要时，什么条件决定优先顺序 |
| 判断校准 | 新信息出现后，原判断保留或调整到哪里 |

每个目标只使用以下状态：

```text
未涉及 / 部分回答 / 已回答 / 已否定 / 说不清 / 已关闭 / 纠正后失效
```

每个问题同时记录认识方向、认知动作、被检验的条件或事实、预期获得的判断关系和来源引用。已经回答、否定、关闭或被纠正的目标退出候选；新证据或纠正可以重新打开受影响目标。

## 4. 选题与提问方式

### 4.1 方向选择

方向采用“用户线索优先、判断标准兜底”：

1. 两条都成立的理由或事实优先进入证据张力；
2. 两项目标互相挤压时进入取舍条件；
3. 明确规则、绝对条件或依赖前提时进入默认假设；
4. 用户动摇、纠正或获得新证据时进入判断校准；
5. 缺少上述信号时，从判断标准开始。

系统一次只选择一个方向。当前方向最多提出三个具体问题；整场会话不设置固定总轮数，有限目标和目标关闭共同控制深度。

### 4.2 单变量对比优先

判断标准、默认假设和判断校准优先使用单变量对比：只改变用户已表达的一个条件，询问判断是否随之变化。问题允许用户回答“都重要、都不是、还要看其他条件或说不清”，不得加入新人物、新动机、新结果或暗示正确答案。

其他问法按以下顺序使用：

1. 具体实例或判断瞬间；
2. 模糊词语澄清；
3. 条件对比；
4. 解释原因。

解释式追问后置；同一认识方向最多使用一次。固定问题模板只作为历史基线，不进入用户可见生成。

### 4.3 认识增量验收

每轮回答与进入当前方向前的理解快照比较：

- 形成预期的新关系时，关闭当前方向并更新成果；
- 回答相关但仍不完整时，继续一个更聚焦的问题；
- 未形成增量时，最多换一次更具体、低负担的入口；
- 再次没有增量或用户说不清时，关闭当前目标并选择其他方向或开放转场。

## 5. 主动推进、说不清与开放转场

达到至少一项认识增量前，AI 默认主动引导。形成一项增量后，系统继续检查未覆盖方向：存在高价值方向时直接提出下一问；缺少合格方向时才进入 `transition`。

用户只说“继续”时：

- 有合格方向：选择最高优先级方向并提出下一问；
- 无合格方向：进入一次开放探索；
- 再次只说“继续”且仍无方向：保持开放输入、日志和退出，不制造问题。

开放转场使用明确文案：

> 如果这件事里还有哪个判断、矛盾或选择让你拿不准，可以直接告诉我；也可以先生成日志。

用户表达不确定可以形成有效认识；第一次说不清只换一次低负担入口；第二次仍说不清时只关闭当前目标。明确拒绝、停止或退出立即执行用户边界。

## 6. thinkingSummary 与成果来源

每个正式提问轮包含一至两句 `thinkingSummary` 和一个正式问题。`thinkingSummary` 只负责：

1. 说明 AI 当前看见的条件、张力、区别、取舍或校准；
2. 解释下一问准备确认什么，以及为什么值得确认。

原话引用、同义复述、事实堆叠、问题改写、答案预告、第一人称冒用和内部术语均为失败。

成果按来源分流：

- 用户自己说清成果且没有下一问：直接保存并开放转场，不新增 AI 认识文案；
- 用户自己说清成果且还有下一问：思路只解释剩余缺口和下一问理由；
- AI 综合形成新关系：展示该新增关系一次；
- 用户纠正：展示理解变化一次，旧关系退出；
- 同一成果后续只作为内部上下文，不再重复展示。

## 7. 纠正、来源和 AI 综合边界

纠正是高优先级重规划动作：识别纠正对象、撤销旧事实或关系、保存新内容、失效依赖旧理解的成果、重建判断地图并继续选择问题。纠正本身不得触发对话结束；用户同时停止时，停止优先。

AI 每次最多形成一条当前事件内关系，关系两侧都要有用户来源。允许条件影响判断、证据支持或削弱判断、证据张力、取舍条件、判断校准和信息不足。人格、长期价值、隐藏动机、他人动机、道德评价、长期规律、无来源因果以及“唯一、真正、根本”等排他结论继续禁止。

## 8. 语义重复门

重复按照“期待获得的答案和判断关系”判定。问题签名为：

```text
认识方向 + 认知动作 + 核心条件 + 预期关系
```

发送前对照当前有效事实、用户最新回答、已有成果、历史问题签名以及目标状态。换词、换句式或换目标名称后仍索取同一答案时一律阻断。

候选目标已有答案时，系统关闭该目标并选择下一方向；目标有效但第二段文案重复时，只允许一次携带具体原因的定向重写；仍重复时阻断并选择其他目标或开放转场。

## 9. 入口与模型职责

单角度入口只确认“一个具体事件 + 用户想理清的个人困扰”。个人困扰可以是判断、犹豫、担心、感受、行动顾虑或关系困惑。只有事件时询问想理清的判断、犹豫或顾虑；只有困扰时询问对应的具体事件；双事件先聚焦并只使用归属于当前事件的材料。门槛满足后自动进入“理清想法”，移除四角度选择和第一检查点。

正式回合继续使用两段式：

```text
第一段模型：更新有限判断地图和来源
→ 系统：处理边界、目标状态、方向优先级、问停和提问方式
→ 第二段模型：生成 thinkingSummary + 一个问题
```

第一段不自由生成问题、`answerEntry`、用户可见成果或整段结束动作。系统负责产品决策；第二段只负责自然表达。正式内容问题使用 DeepSeek 官方 API，Preview 前必须通过真实 Provider、地址、模型和候选版本预检。

## 10. 失败与恢复

- 临时 Provider 问题自动重试一次；
- 格式或表达问题固定认识方向、预期增量和来源，定向重写一次；
- 重复、旧纠正内容、无来源事实、忽略停止和越界推断直接阻断；
- 正式复盘不使用 baseline 或“简单模式”伪装成功；
- 最终失败保留用户原话、判断地图和当前进度，展示具体原因、错误码、Request ID 与重新生成入口；
- 配置、账户、地址、模型或候选版本不一致时在 Preview 和部署前阻断。

## 11. 分层验证与退出条件

### 11.1 稳定性小门

先执行 `10` 个决策点，每个独立运行 `3` 次，共 `30` 个正式结果，覆盖只有判断、只有依据、基础材料齐全、张力、取舍、纠正、语义重复、第一次和第二次说不清、停止及开放转场。

硬门：动作 `30/30` 正确；重复、旧纠正、纠正后错误结束、忽略停止、原话复述、第一人称冒用和 Ark Trace 均为 `0`。认识方向与问题至少 `27/30` 可原样使用，剩余最多为轻微表达问题，同一种目标选择错误不得重复。

### 11.2 自动与人工 Preview

稳定性小门通过后，执行单角度自动 `8+2`，脚本必须根据 AI 实际目标选择回答，隐藏信息未消费或动作需要重选时直接失败。随后完成 `4` 条人工实聊：`2` 条真实事件和 `2` 条风控事件，至少 `3` 条通过、最多 `1` 条条件通过、失败为 `0`，四条都完成日志生成、编辑、保存、刷新和重新打开。

GI-051 的双延迟、日志来源和安全阻断继续生效。全部通过后只进入 Production 人工授权等待；Production 切换仍需要产品负责人单独批准。
