## 2. 为什么现在要单独讨论等待问题

GI-088 过去重点提高“最终能否拿到可见答案”。自动恢复、调整超时和切换官方 Pro 都服务于这个目标。官方 Pro 的历史等待已经达到 `22.0 / 25.4 / 42.5` 秒，平均约 `30` 秒；这项体验风险当时已经成立。

当前两题探针再次暴露等待问题：两次都很快通过鉴权、模型检查和 HTTP 连接，随后连续等待正文，最终在 `45` 秒正文空闲门停止。用户在这段时间内看不到可用回应。

产品负责人已经否定“把等待上限增加到 120 秒”作为解决方案。接下来先查清速度根因，再决定候选、模型或回答链路如何调整。

## 3. 当前一句话结论

历史工作正确修复了若干空正文和误超时问题，同时把“输出可靠性”作为主要目标；用户可感知速度一直缺少独立硬门。当前长等待很可能由 `Pro + high 思考 + 完整 JSON 整段返回 + 更复杂的新合同` 共同放大，具体主因仍需单因素证据确认。

产品负责人已确认日常合格线为 `45` 秒内出现针对用户内容的有用回应、`60` 秒内完成可见回答，并接受“先回应、后完成结构化理解与记录”的两段式方向。首轮 RPR-CF-02 合同 A/B 已按 `A-B-B-A` 完成：A1 `22.687` 秒、B1 `26.423` 秒、B2 `49.455` 秒、A2 `33.370` 秒；四次均获得有效正文，首个有用回应门通过 `3/4`，60 秒完整可见门通过 `4/4`。

两次 B 均慢于配对 A，差值分别为 `3.736` 秒与 `16.085` 秒；只有一组达到预设的 10 秒方向门，因此新增合同负担仍是可疑因素，当前证据无法将其确认为本次长等待的单独原因。裁决已封存为 `inconclusive_mixed_direction`，4 次额度耗尽，停止自动追加调用。

## 5. 历史做法为什么没有解决速度

| 历史阶段 | 当时发现 | 当时方案 | 解决范围 | 仍然保留的问题 |
|---|---|---|---|---|
| v0 | `max_tokens=1600` 被隐藏思考占满 | 取消应用层 Token 上限 | 修复一种确定的空正文原因 | v1 仍有 12 次空正文、7 次超时 |
| v2～v3 | HTTP 200、隐藏思考存在、可见正文为空 | 空正文后自动再调用一次 | 提高最终拿到正文的概率 | 最坏需要两次完整调用，等待增加 |
| v4～v5 | 本地 30 秒会切断仍在生成的请求 | 拆分响应头、正文空闲和总时长 | 避免误杀慢请求，获得更清楚的计时 | 模型生成速度保持原状 |
| v7r1 | Prefix 续写与 JSON Output 冲突 | 放弃 Prefix，比较不同模型 | 排除一条不可用恢复路径 | 速度问题继续存在 |
| v7r4～v8 | 官方 Pro 的可见正文更稳定 | 选择 Pro，保留 high 和 JSON | 首次可见正文可靠性提高 | 历史平均等待约 30 秒 |

因此，历史根因判断需要分开看：

1. `max_tokens` 和本地 30 秒误切断属于已确认根因，相关修复有效。
2. 后续只定位到“上游完成思考却缺少可见正文”的可观测边界，供应商内部原因没有查明。
3. 自动恢复和更长等待主要保护最终结果，用户速度缺少对应改造。
4. 过去把 HTTP 成功、正文最终可见和内容质量放在主要裁决里，等待时长长期停留在风险说明。

## 6. 当前根因候选

### 已确认

- 当前连接、鉴权和模型列表可用。
- 主要时间消耗发生在 HTTP 响应头之后、完整正文到达之前。
- 完整 JSON 整段返回会让用户在模型完成全部工作前持续等待。
- 旧的空正文自动恢复需要先拿到一个完整响应；当前请求在正文完成前就超时，因此这条恢复路径无法处理本次问题。

### Codex 当前判断

- `deepseek-v4-pro + high` 本身具有明显长等待风险，历史数据已经支持这一点。
- 当前 `relationship_claim_status_v1` 增加关系解释清单、状态和多个使用位置，模型的判断与输出负担高于上一候选，可能进一步放大等待。
- 当前合同相较上一成功候选，本地只读测量显示：系统说明约增加 `22%`，输出合同约增加 `37%`。这是一项待实验验证的关联证据。

### 首轮 A/B 后仍待验证

- 新合同复杂度是否是本次长等待的主要原因；首轮两组差异强度不一致，归因保持开放。
- 同一时段的供应商负载是否显著影响结果。
- 降低思考强度、切换模型或拆分响应链路后，内容质量能否保持。
- 45 秒有用回应与 60 秒完整可见回答能否在真实页面体验中成立；该项留给未来 Preview 验证。

## 7. 已确认的产品决定

1. 日常合格线：`45` 秒内出现针对用户当前内容的有用回应；通用等待提示只承担状态反馈。
2. 完整可见回答：`60` 秒内完成。
3. 接受“两段式体验”作为后续产品方向；本轮先归因，暂不实现页面链路。
4. 第一个真实单因素为合同 A/B；固定 RPR-CF-02，采用 `A-B-B-A` 四次串行，降低先后顺序和同一时段波动的干扰。

## 8. 推荐的排查顺序

### 第一步：零调用检查

- 对比上一成功候选和当前候选的完整请求差异。
- 标出重复说明、重复状态和可以由程序推导的字段。
- 设计一个更精简的合同草案，保留“用户已明确／待确认假设”的产品能力。
- 这一步只形成讨论材料，不改变候选。

### 第二步：单因素真实对照（已完成）

全新启动卡、运行器、封存器和自动测试已经完成，身份为 `2026-08-16.gi088-response-latency-contract-ab-v1`，计划指纹为 `d09a2f0d…ac752d`。四次调用使用同一道题、同一模型、同一 high、同一 JSON 设置：

- RPR-CF-02 按 `A-B-B-A` 运行上一成功候选与当前候选；
- 响应头上限 15 秒，首个有效正文门 45 秒，正文与总观察上限 60 秒；
- 并发 1，重试、恢复和降级均为 0。

实际结果：

| 运行 | 合同 | 响应头 | 正文 | 总耗时 | 45 秒门 | 60 秒门 |
|---|---|---:|---:|---:|---|---|
| A1 | 上一候选 | 0.398 秒 | 22.289 秒 | 22.687 秒 | 通过 | 通过 |
| B1 | 当前候选 | 0.394 秒 | 26.029 秒 | 26.423 秒 | 通过 | 通过 |
| B2 | 当前候选 | 0.301 秒 | 49.153 秒 | 49.455 秒 | 未通过 | 通过 |
| A2 | 上一候选 | 0.403 秒 | 32.967 秒 | 33.370 秒 | 通过 | 通过 |

两组配对中 B 都更慢；`B1-A1=3.736` 秒，`B2-A2=16.085` 秒。差异方向相同，强度未稳定达到预设门，合同负担只形成弱方向迹象。响应头均在约 0.3～0.4 秒，主要波动集中在正文生成阶段。

公开结果沿用技术回执中的 `conclusion=pending_deterministic_directional_finalization` 作为“运行阶段已完成、等待封存器裁决”的阶段标记；同一回执随后写入的 `status=sealed_directional_result`、`decision=inconclusive_mixed_direction` 与 `nextStep` 承担最终裁决。封存器已被调用前指纹绑定，本轮保留原始字段以维持证据身份。

四次结果只形成方向性证据；正式稳定性和页面端到端体验结论需要后续独立预算与 Preview 授权。

### 第三步：根据归因选择方案

- 合同负担为主：精简合同，并复测语义修复与速度。
- 模型或思考强度为主：比较更快配置，同时守住内容质量。
- 整段返回链路为主：讨论快速用户回应与后台结构化处理的两段式产品方案。
- 供应商波动为主：建立多时段稳定性门，并评估备用模型或降级路径。

### Prompt、Skill 与程序的职责建议

本轮合同 A/B 保持 A、B 原始 Prompt 与 Skill 不变，只观察合同差异对应的等待方向，因此本轮没有实施 Prompt 精简、Skill 精简或职责迁移。

Codex 对后续优化的建议是同时推进两件事：程序接管可确定、可校验的职责，并据此精简 Prompt 与 Skill。程序适合承担来源校验、权限与预算、状态不变量、可推导字段、格式整理和失败恢复；模型继续承担用户语义理解、已明确事实与待确认假设的区分、当前焦点选择和自然回应。该建议目前属于后续方案方向，尚未形成候选或发布结论。

## 9. 当前明确停止的做法

- 延长到 120 秒不再作为速度修复建议。
- 自动重试不承担速度改善结论。
- HTTP 200 不代表用户体验通过。
- 等待提示只能缓解不确定感，不能证明响应速度合格。
- 当前 `relationship_claim_status_v1` 继续保持“语义未知”，不进入完整 10 题、Judge、隐藏集、真人 Preview 或发布。
