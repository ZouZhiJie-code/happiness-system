# GI-088｜先回应后整理与职责重划实施计划

## 1. 为什么要同时做两件事

产品负责人确认两个目标同时成立：用户发送后要尽快收到有内容的回应，模型完成整轮工作的总耗时也要继续下降。

当前单段 JSON 把给用户看的回应、语义理解、状态变化和记录字段放在同一次完整返回中。首轮合同 A/B 的响应头仅约 `0.3～0.4` 秒，主要等待发生在正文生成阶段；B2 在 `49.455` 秒后才一次显示全部内容。这条链路会把后台整理时间全部转化为用户空白等待。

历史证据已经回答两项问题：

- 官方 Pro 的 `reasoningEffort: high → low` 确实带来速度收益。完整开发重跑中，Low 的 P50／P90／最长为 `19.886 / 30.955 / 38.554` 秒，速度门通过；该轮因 `3` 次空正文、`4` 次来源遗漏和 `1` 次动作违规形成 `no_go_technical`。
- 完整合同与可执行精简合同＋程序投影已经进行 `126` 次调用对照。完整组与精简组 P50 为 `35.042 / 32.085` 秒，P90 为 `50.215 / 54.127` 秒，两组均未通过速度门；精简组的主要失败是来源责任重复。来源继承职责随后由程序重划并通过零模型回放。

因此，本轮继承 Low 的速度方向和程序来源继承结论，不重复 High／Low 对照，也不把“减少 Prompt 字数”直接当成速度结论。

## 2. 已确认的产品方向

### 第一段：先给用户有内容的回应

- 使用官方 `deepseek-v4-pro`，Thinking 开启，`reasoningEffort=low`。
- 输入只包含当前对话所需上下文、用户控制边界和可见回应要求。
- 输出只包含自然理解与自然回应，不生成任务账本、认识状态、关系使用位置或记录字段。
- 结果一旦通过可见内容安全门，运行入口接入后就通过现有 SSE 通道发给页面。

### 第二段：随后完成理解与记录

- 第一段回应冻结后，第二段读取同一用户输入、当前状态和第一段原文。
- 初始兼容候选继续使用 Pro High，只生成当前结构化语义结果；第一段文字由程序直接合成，因此第二段无法改写已经显示的内容。
- 程序负责编号、已有来源继承、允许动作、状态迁移、字段补齐、幂等、预算、保存与失败恢复。
- 模型继续负责新语义判断：当前焦点、用户已明确事实、待确认假设、认识增量和下一问。

第一段回答承担用户可感知体验；第二段完成后再更新记录状态。第二段失败时保留用户原话与第一段回应，并进入可恢复状态，不能让已经显示的回应在刷新后消失。

## 3. 本轮本地实施范围

- 新建独立候选 `2026-08-16.gi088-response-first-two-stage-v1`。
- 建立第一段可见回应合同、第二段兼容结构合同、程序合成与一致性校验。
- 建立 Prompt／Skill／程序职责清单，并生成语义精简候选草案。
- 记录当前完整候选、第一段候选和第二段候选的字符数、字段数及职责数量；这些只承担零调用关联证据。
- 使用合成数据验证两段顺序、第一段提前可见、第二段合成、来源与状态保护、失败恢复状态和公开证据边界。

本轮保持产品运行入口、数据库结构和现有候选不变。真实 Provider 调用、Judge、隐藏集、真人提交、Preview、Production、提交、推送和部署均为 `0`。

## 4. 职责边界

| 工作 | 模型 | 程序 |
|---|---|---|
| 理解用户最新表达 | 负责 | 校验输入来源存在 |
| 区分用户已明确与待确认假设 | 负责 | 校验状态和可使用位置 |
| 选择焦点、下一问与自然表达 | 负责 | 校验动作是否允许、问题是否符合当前状态 |
| 生成新认识摘要 | 负责 | 生成编号、合并历史来源、应用新增／修订／撤回 |
| 继承已有任务和已有来源 | 提交本轮变化 | 读取并合并历史状态 |
| 关系解释使用索引 | 按数组位置声明语义引用 | 生成 `RC1、RC2…` 编号并阻止越权使用 |
| 权限、预算、幂等、保存、恢复 | 提供结果 | 负责 |
| 页面先显示、后台再整理 | 提供两段内容 | 负责顺序、状态和失败处理 |

## 5. 验证门

1. 第一段合同中结构化状态字段数量为 `0`，只输出用户可见内容。
2. 本地状态机在第二段开始前进入 `response_visible_structure_pending`；现有 SSE 与客户端已具备提前交付 `onDelta` 的通道，运行入口接入继续待后续验证。
3. 第二段只返回语义，程序直接合成第一段回应；结构结果无法通过时，记录为可恢复的结构阶段失败。
4. 程序生成关系解释编号、继承已有来源并校验动作、关系状态、使用范围与状态不变量。
5. 第一段成功后进入 `response_visible_structure_pending`；第二段失败时进入 `structure_failed_recoverable`，原话和可见回应可恢复。
6. 自动测试、类型检查、定向 ESLint、JSON、文档链接、公开内容边界和差异格式通过。

## 7. 首轮真实证据

本地候选通过后，真实调用需要两本独立账：

- 体验账：只判断第一段是否在 45 秒内出现，完整可见回应是否在 60 秒内完成。
- 根因账：分别记录第一段与第二段的 Prompt 长度、输入／隐藏思考／可见输出 Token、响应头、正文和总耗时；同一轮只比较一个主要因素。

候选的语义质量、页面端到端体验和记录可靠性继续使用各自证据。

本轮使用新身份 `2026-08-16.gi088-visible-contract-burden-ab-v1`，固定 RPR-CF-02、Pro Low、同一完整用户输入、同一 Provider 与同一时段，按 `A-B-B-A` 比较：

- A：当前 `relationship_claim_status_v1` 完整合同，思考强度改为 Low；
- B：本候选第一段可见合同，思考强度同为 Low；
- 预算授权并消耗 `4/4`，并发 `1`，重试／恢复／降级均为 `0`；
- 只判断可见 Prompt／输出合同负担的延迟方向，不承担语义质量或产品验收。

两臂使用同一份完整用户载荷，只改变可见 Prompt、Skill 与输出合同这一组模型工作负担。产品负责人已于本会话明确授权独立 `4` 次调用预算；运行完成后按额度停止。

执行身份固定为 `2026-08-16.gi088-visible-contract-burden-ab-v1`，计划指纹为 `95c920d8…d03be`，启动卡 SHA-256 为 `8fef9c01…a30ce`。A 使用当前 `relationship_claim_status_v1` 完整 Prompt／Skill／输出合同，B 使用两段式候选的第一段可见 Prompt／Skill／输出合同；两臂均使用 Pro Low、同一完整用户载荷、同一 Provider、同一输出上限和同一运行时段。响应头上限为 `15` 秒，正文与总观察上限为 `60` 秒；并发 `1`，重试、恢复和降级均为 `0`。
