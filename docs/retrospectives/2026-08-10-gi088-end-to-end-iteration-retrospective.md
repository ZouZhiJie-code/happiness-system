## 1. 先说结论

### 1.1 这轮实操真正验证了什么

GI-088 证明了一个很重要的事实：高质量 AI 访谈的难点，同时存在于模型内容、程序状态、用户控制、失败恢复、评测工具和证据治理六条链路。任何一条链路出现高影响小缺口，都可能让已经付费、已经等待、内容本身有效的一轮访谈失去价值。

这轮迭代获得了五项明确成果：

1. Thinking high 的内容方向优于关闭配置，后续正式候选收口为 high-only。
2. 官方 DeepSeek V4 Pro 的可见正文可靠性已经达到继续使用条件。
3. “单一回答焦点”比“一个问号”更准确地控制用户回答负担。
4. 语义变化由模型输出、确定性状态由程序维护，是长轨迹连续性的正确职责划分。
5. 真人评测必须建立在可靠的评测底座上；程序可验证问题在人进入页面前清零，真人时间只用于体验和内容判断。

这轮也暴露了四类系统性问题：

1. **产品原则被表面规则替代。** 一个回答焦点被编码成一个问号，事件里的“累”被升级为停止访谈。
2. **自动测试验证旧规则的执行，缺少对规则合理性的反例审查。** 多轮测试全绿，最终批次仍在 A1 被小规则阻断。
3. **评测对象与评测工具一起变化。** 模型、Prompt、状态合同、恢复、页面和封存能力交叉迭代，真人结果经常被底座问题污染。
4. **协作过程缺少稳定的当前摘要。** 讨论、计划、授权和执行多次错位，历史问题一度丢失，技术结论也曾难以从产品视角理解。

### 1.2 这轮最大的成本

模型费用只是其中一部分。主要成本来自评测者的上下文切换、重复等待、手动重试、重新部署页面、重建评测批次和重新理解问题。

几个代表性数字：

| 检查点 | 结果 |
| --- | --- |
| 正式版本目录 | v0～v8r1，共 14 个阶段性版本 |
| v1 | 66 次调用；37 有效、10 程序保护、19 技术失败、17 手动重试 |
| v1 真人完整性 | 16 条轨迹只有 2 条全程无失败，12 条以失败结束 |
| v5 | Preview 与空白批次完成，严格单问号原则随后被撤回，未形成真人价值 |
| v7 | 11 个用户轮次、19 次调用；8 次空内容、1 次超时、1 次程序保护 |
| v7r2 Ark Flash | 15 次提交、20 次调用；首次直接成功 10/15 |
| v7r4 V4 Pro | 12 次提交、13 次调用；首次可见正文 11/12，空内容 0 |
| v8 | 10/10 首次成功，7 条提问全部为同一焦点、低负担 |
| v8r1 | 最终 12 项首项即被意图误判提前终止 |

因此，未来优化目标要从“更快产生下一个候选”升级为“每一张真人页面都只验证真人才能判断的问题”。

## 3. 完整版本时间线

### 3.1 v0｜第一次发现 Thinking 输出预算问题

**目标**

建立 12 项 off/high 配对真人评测，观察 Thinking 对内容质量和运行可靠性的影响。

**发生了什么**

A2 high 同一用户轮次连续三次在 `completionTokens=1600` 时结束，`reasoningTokens` 同样为 1600，可见正文为空。v0 共 9 次正式调用：3 次有效、3 次程序保护、3 次技术失败。

**已确认根因**

应用层 `max_tokens=1600` 同时承载隐藏推理和最终可见答案。真实多轮 high 输入下，推理占满预算，答案失去生成空间。

**经验**

短冒烟通过无法代表长上下文。输出预算、推理 Token、可见答案 Token需要分账；重试相同预算只会重复同一失败。

**转向**

v1 只移除应用级 `max_tokens`，保持模型、Prompt、Skill 和任务不变。

### 3.2 v1｜首批真人质量基线与技术噪声暴露

**真人结果**

- A1～A8 完成，`8/12` 主动提前结束；16 条独立轨迹。
- 66 次调用：37 有效、10 程序保护、19 技术失败、17 手动重试。
- high 的 19 次技术失败包括 `EMPTY_CONTENT 12` 和 `TIMEOUT 7`。
- 产品负责人在 8 项比较中判断 high 6 项更好、2 项相当。
- 关闭配置有 7 次程序保护，high 同时承担更长等待和更多技术故障。

**产品负责人判断**

high 的自然表达、问题切入、认识深度和总结质量形成明显优势；频繁故障严重打断访谈，当前 8 项已经足以进入复盘。

**Codex 初评**

内容优势成立，技术链路无法承载连续真人访谈。下一步应先恢复连续完成能力，再扩大质量样本。

**额外发现**

- A4、A6 和 A7 high 没有真正触发目标能力，无法承担对应能力通过证据。
- 旧运行器只允许 `12/12` sealed；产品已经结束，数据库仍为 `running`。
- 导出要求 sealed，8/12 只能借助私有快照和哈希临时封存。
- 产品评价与 Codex 评价曾把技术完整性和内容质量采用不同口径，形成表面分歧。

**经验**

任务执行、目标触发、内容质量、技术完整性和端到端体验需要分别记账。提前结束属于有效评测决策，运行器需要原生表达。

### 3.3 v2 Diagnostic｜先补评测底座，再做配对诊断

**完成内容**

- `early_stopped`、部分导出、未执行任务、目标触发确认。
- 响应头、正文读取、总时长和中止来源的安全诊断。
- response format 6 次配对探针。
- Thinking high/disabled 4 次配对探针。

**探针结果**

- JSON Output：2 valid / 1 empty。
- 普通文本 JSON：1 valid / 1 empty / 1 schema invalid。
- Thinking high 和 disabled 四次重放全部有效，历史空内容未稳定复现。

**确认结论**

移除 JSON mode 无法解决空内容，还增加结构漂移。Thinking 是否为主要诱因缺少充分证据。可以确认的近端机制是：上游返回 HTTP 200、正常 stop、隐藏推理存在、可见正文长度为 0。

**经验**

配对探针适合排除错误方向，也可以形成 inconclusive 结论。供应商内部原因无法继续观测时，尽早收口“可行动根因边界”，把精力转向用户可见恢复。

### 3.4 v3｜空内容恢复被下一层状态问题抢先阻断

**主要因素**

首次 `EMPTY_CONTENT` 后沿相同 high 配置自动恢复一次，失败和恢复分别留痕。

**真人结果**

A1 完成后 `1/12 early_stopped`，共 8 次调用。空内容和自动恢复均未触发，off/high 都在阶段 2 回答机会用尽后再次创建新机会，被程序保护。

**已确认根因**

模型知道阶段 2 没有剩余机会，仍输出“阶段 2＋新问题”。

**经验**

修复一个问题后，真人可能先撞到另一个底座阻断。候选开门前需要对整条状态机做零模型回放，避免当前主要因素根本没有机会被验证。

### 3.5 v4｜阶段自然转场通过，30 秒硬截止暴露

**主要因素**

阶段 2 机会用完后，有认识且用户打开更深未解部分时进入阶段 3；条件不足时总结或暂停。

**真人结果**

A1 off/high 共 10 次调用，`1/12 early_stopped`。high 得到阶段转场的单例支持；后两次 high 首次调用都在 30 秒本地总截止被中止，off/high 也各出现双问题。

**已确认根因**

两个超时在约 0.43 秒已经收到响应头，正文持续生成到 30 秒时被本地 `hard_total` 主动切断。连接已经建立，健康生成被误判为超时。

**经验**

超时需要拆成响应头等待、正文空闲和整次上限。业务阈值需要依据真实 Trace 校准。

### 3.6 v5｜高可靠性方向正确，单问号形成过度修复

**主要因素**

- high-only。
- 15 秒响应头、45 秒正文空闲、60 秒总时长。
- 一轮只允许一个问号和一个可见问句。

**结果**

Preview 与 0/12 空白批次已经完成，产品讨论随后确认“用户回答负担”的控制单位应为一个独立回答任务。主问题、澄清、举例和选项可以自然形成两三个问句。v5 因此未形成独立真人裁决。

**已确认根因**

问号数量无法判断用户需要组织几个独立答案。

**经验**

这是最典型的过度修复：工程把语义目标收紧成表面信号，自动测试越完整，错误规则越稳定。产品原则需要在完整实现和部署前先经过正例、相邻正例、反例和隐藏反例校准。

### 3.7 v6｜单一回答焦点获得真人通过

**主要因素**

多个问句共同服务一个 `answerTarget`，用户能够用一段连贯回答覆盖时，允许正常提交。问号数量只用于观测和抽检。

**真人结果**

- A1、A2 完成后 `2/4 early_stopped`。
- 11 条可见提问：9 条同焦点自然可答，2 条同焦点表达偏重，独立多任务 0。
- 17 次调用；1 次正文停滞超时并自动恢复成功；空内容 0。

**产品负责人判断**

原有问题已经解决，A3、A4 无需继续。

**新问题**

- `burdenSignal.ref` 等旧完整状态字段仍会拒绝有效结果。
- 轨迹 12 次上限可能中断深聊。
- 页面滚动、历史回看、评价区和导出影响连续体验。

**经验**

程序继续保护一个回答目标、一个回答机会、阶段、来源和状态；同一焦点的自然表达交给模型与人工复核。撤销错误规则同样属于有效迭代成果。

### 3.8 v7｜连续性底座成立，官方 Flash 可靠性成为主阻断

**主要因素**

- 模型只输出 `none / add / revise` 的本轮变化。
- 程序维护认识编号和当前状态。
- 轨迹不显示固定轮次上限。
- 自动失败后提供一次用户主动生成。
- 重做滚动、任务回看、评价区和导出。

**真人结果**

两条轨迹完成，共 11 个用户轮次和 19 次 Provider 调用；出现 8 次空内容、1 次超时和 1 次程序保护。连续性方向获得真实体验，官方 Flash 可见正文可靠性成为主要阻断。

**文档治理问题**

v7 README 仍保留 Preview 创建时的 `0/2` 文案，后续结果由 v7r2 文档和私有导出承接。这说明“版本说明”和“当前运行实况”曾发生滞后。

**经验**

运行实况应由 run/session 和不可变导出承担，README 需要在收口时写入脱敏结果，避免后续会话误读旧起点。

### 3.9 v7r1｜Prefix 方案被一条兼容探针及时拦截

**主要因素**

空正文后复用已经完成的隐藏推理，通过 DeepSeek Beta Prefix 续写最终 JSON。

**结果**

本地实现、隐私封装和自动测试已经完成；唯一一次兼容探针在生成前返回：`response_format json_object should not be used with prefix`。Preview 和建批及时停止。

**经验**

这次停止是正确的，同时揭示顺序可以继续优化：供应商特殊参数组合应先做最小兼容探针，通过后再完成完整服务、UI 和恢复实现。

### 3.10 v7r2｜Ark Flash 小探针方向成立，真人稳定率未过门

**主要因素**

只切换到火山 Ark Flash，保留 Thinking high、JSON mode 和 v7 合同。

**真人结果**

两项完成；15 次提交、20 次调用；首次直接成功 10/15，自动恢复成功 3 轮，最终程序保护 2 次。两项均为 `minor_issue`，可靠性门 No-Go。

**已确认根因**

模型只提交本轮新增来源，旧程序要求每轮重复完整历史来源。长轨迹让确定性状态责任落在模型身上，最终产生来源血缘保护。

**经验**

三条平台探针能够筛选方向，无法证明正式稳定率。v7r2 真人结果及时纠正了小样本外推。

### 3.11 v7r3｜用零模型回放把确定性状态交给程序

**主要因素**

程序合并历史来源、去重并保持顺序；纯停止零调用；新内容加停止最多调用一次，最终由程序强制暂停。

**验证**

使用 v7r2 两个真实失败输出做私有零模型回放，状态来源和停止路径均通过。v7r3 未创建真人页面。

**经验**

这是本轮最值得复用的低成本做法之一：确定性程序问题先用真实失败输出回放，验证通过后再改变模型或平台。

### 3.12 v7r4｜V4 Pro 可靠性达到继续使用条件

**主要因素**

继承 v7r3，只切换到官方 DeepSeek V4 Pro。

**真人结果**

- 2/2 完成；12 次提交、13 次调用。
- 首次产生可见正文 11/12，`EMPTY_CONTENT=0`。
- 9/12 首次通过全部程序校验。
- 1 次正文空闲超时经自动恢复完成。
- 2 次有效模型输出因程序保护未提交。

**产品负责人判断**

整体 No-Go，继续使用 V4 Pro；程序修复后进入 v8。当时成本估算显示，每 1,000 次六轮访谈的模型成本预计增加约 26～46 元，可靠性收益足以覆盖该差异，正式接入前仍需重新核价。

**已确认根因**

- 可确定的来源补全发生在严格校验之后。
- 组合停止覆盖不完整。
- Skill 缺少统一问前决策。
- 自动恢复缺少整条自动链的共享等待上限。

**经验**

模型可靠性与程序成功率必须分账。有效模型结果被程序保护时，继续换模型不会解决根因。

### 3.13 v8｜统一问前决策获得产品通过

**主要因素**

每轮先采用用户继续、停止或纠正意图，再吸收已有内容、寻找未解部分、判断认识增量，并提供具体低负担入口。程序同时补全可确定来源，自动恢复共享 90 秒。

**真人结果**

- A1 共 10 次提交后 `1/4 early_stopped`。
- 10/10 首次调用成功。
- 7 条可见提问全部为 `same_focus_low_burden`。
- 技术失败、恢复、人工重试、程序保护和重复消息全部为 0。

**产品负责人判断**

`direct_use / target triggered / 通过`。

**Codex 初评**

核心行为通过；“很好，就聊到这吧”被当成新内容加停止，多产生一次 17.514 秒调用。

**经验**

一条轻微问题可以通过零模型小修进入下一阶段，前提是小修本身的语义边界已经经过反例校准。

### 3.14 v8r1｜最终 12 项被控制意图误判阻断

**主要因素**

将简短礼貌回应加明确停止识别为纯停止，随后直接进入最终 12 项。

**真人事故**

A1 中，用户描述“向奶奶解释很累”。系统把事件里的疲惫判断为停止当前访谈，覆盖了模型已经生成的有效回应，页面显示暂停并封存当前分支。

**产品负责人判断**

“累、烦、解释费劲”在这个场景属于访谈内容；用户明确要求停止当前访谈时才执行停止。当前最终批次已经被小规则阻断。

**已确认根因**

1. 宽泛疲惫词面缺少说话人、作用对象、否定、转述、时间和撤回判断。
2. GI-088 把 `fatigue_feedback` 直接升级为停止资格。
3. 程序接管具有不可逆优先级，后续有效模型判断无法撤销误判。
4. 现有意图数据集缺少“词面相近、控制意图相反”的反事实案例。

**扩展审计发现**

同类风险覆盖：“我很累，但还想继续聊”“我不想生成日志，继续问我”“她说别问了”“别切到感谢”“我换个角度想”“我当时觉得够了”等表达。

**当前转向**

v8r2 将全部已确认 P0/P1 一次修复，内部按用户控制、结果事务、评测治理三层开门，最终只交付一个新 Preview。约 200 轮工程容量由产品负责人接受，本轮明确排除优化。

## 4. 我们踩过的坑

## 4.1 产品与规则设计

### 坑 1｜把用户结果压缩成表面信号

代表案例：

- 一个回答焦点 → 一个问号。
- 事件里的疲惫 → 停止访谈。
- “换个角度想” → 跳过当前问题。
- “我不想生成日志” → 命中生成日志词面。
- 内容已经充分 → 模型可以自行暂停。

这些规则具有共同特征：实现容易、测试容易、解释直观，同时丢失了说话人、作用对象、肯否、转述和当前共同任务。

**经验**

先冻结用户结果，再选择判尺。高影响控制只有同时满足“用户本人、肯定表达、指向当前访谈、当前仍然有效”时才能改变流程。证据不足时继续访谈并进入复核。

### 坑 2｜一个主要因素被执行成一个很小的代码改动

单因素迭代帮助我们区分 JSON、Thinking、超时、阶段、状态和模型平台；它也带来了 v3～v6 的页面和版本快速增长。

单因素原则适合因果不清的模型、Prompt 和 Provider 实验。已经确认且彼此耦合的评测底座问题，适合在同一开发周期合并修复，内部用分层自动验证保留可归因性。

### 坑 3｜历史问题队列建立过晚

问题曾分散在 v1 Bad Case、每个版本 README、私有导出和侧边讨论中。用户多次追问“历史问题在哪里”“最近的语义问题去哪里了”。

**经验**

首批真人结果出现后就维护唯一问题台账。严重度、实施依赖、当前状态和目标版本分开表达；每次真人收口立即更新。

## 4.2 模型、平台与恢复

### 坑 4｜对黑盒内部原因追得过深

我们依次验证 response format、Thinking 模式和历史请求复现。探针能够排除部分方向，却无法解释 DeepSeek 内部为什么在正常 stop 后只产生 reasoning。

**经验**

根因分三层：

1. 近端机制：我们直接看到什么。
2. 项目可控根因：项目能够修改什么。
3. 供应商内部原因：当前无法观测什么。

达到第二层后即可进入恢复、模型对照或平台对照，避免反复消费小样本。

### 坑 5｜特殊 API 能力在完整实现后才做兼容探针

v7r1 已经实现 Prefix 隐私封装、服务和自动测试，最终才发现供应商拒绝 `json_object + prefix`。

**经验**

供应商专有能力先做一条最小兼容调用，确认参数、错误形态和隐私边界，再开发完整产品链。

### 坑 6｜小样本探针被赋予了过高期待

Ark Flash 三条历史请求都返回可见答案，连续真人批次首次直接成功只有 10/15。

**经验**

兼容探针证明“能不能用”；定向批次证明“能否改善当前问题”；最终独立批次证明“能否发布”。三者保持不同通过门。

### 坑 7｜恢复一度把操作负担交给评测者

v1 有 17 次手动重试。后续自动恢复又由页面副作用发起，页面刷新、多标签页和网络丢失都可能影响恢复。

**经验**

调用资格、共享截止和次数由服务端原子管理；客户端只展示阶段和用户主动的最终选择。一次用户提交的最坏调用上限继续保持首次、一次自动恢复、一次人工生成。

## 4.3 状态、事务与数据

### 坑 8｜让模型每轮重写完整确定性状态

模型需要重复历史来源、认识、任务和负担引用，轨迹越长越容易漏项、重复和使用陈旧编号。

**经验**

模型输出语义变化，程序维护确定事实：编号、历史来源合并、次数、恢复额度和原子提交。

### 坑 9｜严格校验发生在可确定补全之前

v7r4 中有效模型结果缺少可由当前任务和最新用户消息确定补全的来源字段，程序在补全前先拒绝整轮。

**经验**

先执行确定性标准化，再执行严格合同校验；未知、跨任务和虚构来源继续拦截。原始输出和最终有效状态分别保存。

### 坑 10｜批次 revision 包围一次长模型调用

模型调用期间，另一标签页保存人工分类会推进同一批次 revision。Provider 已经返回有效结果后，最终保存仍使用旧 revision，可能丢失付费结果并留下 processing。

**经验**

Provider 结果先按 callId 永久落账，业务状态随后由可重入 finalizer 提交。CAS 冲突只重试合并和保存，绝不再次调用模型。

### 坑 11｜预约、派发和真实调用没有分清

Provider 初始化在预约之后发生，配置错误可以留下虚假调用数和 pending 状态。

**经验**

Provider 静态校验在预约前完成；调用预算只统计真正 `dispatched` 的请求；派发不确定时进入明确终态，停止自动重发。

### 坑 12｜提交没有绑定评测者当时看到的对话

旧标签页可以把旧问题答案提交到新一轮，也可以基于旧对话评价或封存后来新增的内容。

**经验**

用户提交绑定最后可见 assistant；提问评价绑定 observation fingerprint；轨迹评价绑定完整 review snapshot。陈旧请求零模型调用拒绝。

## 4.4 评测方法与评测页面

### 坑 13｜真人承担了本可自动发现的问题

状态机额度、问号规则、意图近邻、Provider 初始化、CAS 冲突、刷新、断线和陈旧标签页都可以用零模型或 fake Provider 验证，实际却多次在真人页面首次暴露。

**经验**

真人时间用于判断自然度、共情、下一问价值、回答负担和整体体验。程序状态、事务、幂等、版本和导出在人进入页面前清零。

### 坑 14｜任务完成、目标触发和质量通过混在一起

v1 有五条轨迹没有触发指定能力，仍然完成了通用对话和评价。

**经验**

每项分别记录：采集状态、目标触发、产品质量、技术完整、端到端体验和批次资格。未触发轨迹只承担通用证据。

### 坑 15｜程序保护成功被理解成用户体验成功

程序保护避免错误状态写入，但用户当轮收不到任何有效回应。v7r4 有两次模型有效输出最终被程序拒绝。

**经验**

保护命中属于安全机制有效，也属于端到端失败事件。两个指标同时保存。

### 坑 16｜评测工具污染了被测体验

评测者一度需要同时聊天、重试、看 Trace、逐轮分类、处理滚动和导出。真实深聊因此反复中断。

**经验**

评测页是测量仪器。聊天阶段保持沉浸，复核尽量放到轨迹结束后；滚动、草稿、回看、错误动作、终态导出和再次下载进入独立开门标准。

### 坑 17｜候选与真人 run 耦合

同一个候选只能有一个批次，当前代码指纹变化还可能阻止历史批次查看和导出。

**经验**

候选描述冻结行为，run 描述一次真人执行。同候选允许多个独立 run；当前指纹只约束写入，历史 run 永久只读。

## 4.5 协作方式

### 坑 18｜讨论阶段过早生成正式计划

用户多次明确要求讨论，Codex直接输出执行计划，导致关键产品原则尚未理解就进入工程表达。

**经验**

讨论固定按“现象—原因—用户影响—方案—代价—产品选择”推进。产品选择确认后再写执行计划。

### 坑 19｜技术结论先于产品结论

指纹、Schema、恢复类型和调用血缘一度出现在回答开头，用户仍不知道“现在能不能继续测”和“其他问题什么时候处理”。

**经验**

每次先用四句话说清：发生了什么、当前测试意味着什么、下一步做什么、其余问题在哪里。技术证据随后展开。

### 坑 20｜授权被拆成过多中断点

用户已经授权一个执行范围后，Codex仍多次暂停确认，造成“任务没有做完”的感受。

**经验**

把允许的代码、Preview、数据库、模型预算、Production 边界和停止点组成一个授权包。授权包内连续推进；只有超出范围的新模型调用、Production 变化、破坏性动作或新的产品选择才暂停。

### 坑 21｜当前状态摘要不稳定

“off 是否仍在运行”“v5 是否使用过”“最近语义问题在哪里”“P0/P1 为什么和处理顺序不同”都曾需要反复解释。

**经验**

每个阶段收口后固定维护一页当前摘要：当前候选、当前 run、已通过能力、问题队列、授权包、Production 边界和唯一下一步。

## 5. 我们做对了什么

### 5.1 真人体验拥有最终裁决权

v1、v3、v4、v6 和 v8 都在证据足够时主动提前结束。它节省了无信息增量的调用，也让“用户觉得对话被打断”成为正式结论。

### 5.2 产品负责人判断与 Codex 独立初评分开保存

v1 先完成盲态九维评分，再读取产品评价，保留了 A2、A5、A6、A8 等真实分歧。产品满意、任务偏离、技术失败和内容可用可以同时存在。

### 5.3 原始失败和恢复血缘长期保留

空内容、超时、保护、手动重试和自动恢复都有独立 Trace。恢复成功不会抹去首个失败，质量评分也不会把恢复结果伪装成首次成功。

### 5.4 Production 边界始终稳定

所有候选保持私有 Preview 与专用评测库，初始化调用为 0；Production 持续运行 `legacy + baseline`。频繁实验没有扩大生产风险。

### 5.5 适时承认因果不充分

response format 探针得到 No-Go，Thinking 探针得到 inconclusive。我们没有把小样本强行写成模型根因。

### 5.6 用真实失败输出做零模型回放

v7r3 和 v8 复用真人失败输出验证程序修复，不消耗新的模型调用，保持了真实语义复杂度。

### 5.7 及时撤销历史过度修复

v6 明确把 v5 严格单问号记录为历史过度修复，恢复到单一回答焦点。错误方案被保留为回归证据，没有继续成为当前产品事实。

### 5.8 对模型路径同时考虑可靠性、内容和成本

v7r4 保留 V4 Pro，依据来自可见正文可靠性、真人轨迹和当时成本估算，决策维度完整。

### 5.9 接受低价值边界，控制范围

产品负责人接受约 200 次用户提交的当前工程容量，本轮不投入极端长轨迹存储重构。产品策略继续不显示固定轮次上限，工程边界保持内部已知。

## 6. 第一性原理根因

### 6.1 表层症状

```text
空正文 / 超时 / 程序保护 / 提前暂停 / 重复重试 / 页面卡住
```

### 6.2 直接机制

```text
上游生成不稳定
本地截止不合理
输出合同互相冲突
表面语义规则越权
状态补全和校验顺序错误
长调用与批次 revision 竞争
```

### 6.3 系统根因

```text
模型、程序、人工复核的职责边界不稳定
候选、运行、页面和证据强耦合
Provider 结果缺少独立事务事实源
高影响控制缺少作用对象与证据
测试集缺少语义近邻和真实故障注入
```

### 6.4 过程根因

```text
产品原则复核晚于完整实现
单因素原则被机械拆成多个页面
唯一问题台账建立较晚
讨论、计划和执行授权频繁交叉
开门标准偏重静态通过，轻视评测仪器可靠性
```

### 6.5 最核心的因果链

```text
产品原则存在语义空白
→ 工程选用容易执行的表面规则
→ 自动测试完整证明旧规则被正确执行
→ 静态门和 Preview 读取全部通过
→ 真人第一条自然表达命中反例
→ 程序取得流程接管权
→ 有效模型结果被覆盖或丢失
→ 整个评测批次失去继续价值
```

未来最重要的改进，就是在“表面规则进入代码”之前加入产品反例门，在“真人进入页面”之前加入事务与故障注入门。

## 7. 未来统一 SOP

## 7.1 阶段 0｜恢复唯一事实源

新会话开始时，只生成一页当前摘要：

- 当前候选、版本、指纹和 runId。
- 当前真实运行状态和调用数。
- 已通过能力。
- 当前 P0/P1/P2 队列。
- 本轮授权包。
- Production 边界。
- 当前唯一停止点。

README、Map 和数据库有差异时，先只读 run/session 和导出，再更新脱敏结论。

## 7.2 阶段 1｜产品规则反例校准

每条高影响规则先覆盖：

1. 明确正例。
2. 相邻正例。
3. 明确反例。
4. 否定表达。
5. 转述与引用。
6. 历史叙述。
7. 后文撤回。
8. 内容加控制。
9. 礼貌表达。
10. 一个表面词对应多个真实意图。

产品负责人先确认用户结果，随后再生成计划和字段。

## 7.3 阶段 2｜零模型行为回放

使用真实历史输出和合成状态覆盖：

- `none / add / revise`。
- 来源补全和未知来源。
- 阶段额度与自然转场。
- 停止、继续、纠正、拒答、跳题和生成。
- 高影响控制的作用对象、肯否、转述和撤回。
- 单一回答焦点。
- 任务目标是否真正触发。

通过门：错误接管 0、错误状态提交 0、历史回归 0。

## 7.4 阶段 3｜真实评测库故障注入

使用 fake Provider、隔离评测库和两个服务实例覆盖：

- Provider 初始化失败。
- reserve、dispatch、结果返回、finalize 各节点中断。
- Provider 成功后数据库冲突。
- 并发人工分类。
- 陈旧标签页提交。
- 陈旧人工评价。
- 刷新、断线、流响应丢失。
- 90 秒自动恢复截止。
- 历史 run 查看和导出。

通过门：已落账 Provider 结果丢失 0；陈旧提交模型调用 0；每段原话 assistant 与状态各最多提交一次。

## 7.5 阶段 4｜供应商最小兼容探针

只有候选依赖新的供应商能力时执行：

1. 一条最小请求。
2. 精确参数组合。
3. 明确预算、重试和降级为 0。
4. 只保存安全诊断。
5. 兼容通过后再实现完整服务和 UI。

## 7.6 阶段 5｜版本与测量仪器开门

要求：

- 行为源码全部进入版本控制和分层指纹。
- 全量测试 0 failed。
- 页面、服务、模型、Thinking、任务集和执行指纹一致。
- 候选与 run 分离；同候选可创建独立复测。
- 初始化模型调用 0。
- early stop、partial abort、部分导出和历史回看可用。
- 聊天、输入、Trace、草稿、评价和下载体验通过。
- 错误都有清晰中文原因、数据保存状态和下一步动作。

## 7.7 阶段 6｜最小真人定向验收

只验证当前需要真人判断的主要因素。技术问题已清零后，1～2 条定向轨迹即可形成方向证据。证据充分时允许提前结束，并立即更新唯一问题台账。

## 7.8 阶段 7｜最终独立完整批次

最终 12 项承担广覆盖发布证据。任何 P0 触发时立即提前封存，避免继续消耗其余任务。全部结果完成后再做产品裁决、Codex 独立评分、调用血缘检查和问题台账收口。

## 8. 以后怎样判断问题归谁处理

| 问题类型 | 主要责任 | 典型例子 | 验证方式 |
| --- | --- | --- | --- |
| 用户结果与边界 | 产品负责人 | 何时停止、什么叫一个回答任务 | 场景讨论与反例确认 |
| 语义质量 | 模型 | 下一问价值、具体入口、自然承接 | 真人评测与人工复核 |
| 确定性状态 | 程序 | 编号、来源合并、额度、原子提交 | 零模型回放 |
| 高影响用户控制 | 程序执行＋人工复核 | 停止、生成、切换、跳过 | 证据门＋反例矩阵 |
| Provider 兼容性 | 适配器 | Prefix、JSON、非流式时序 | 一次最小兼容探针 |
| 运行可靠性 | 服务端 | 落账、恢复、并发、截止 | 故障注入与真实库测试 |
| 内容最终裁决 | 产品负责人 | direct_use、minor、No-Go | 真人完整轨迹 |
| 独立质量审计 | Codex | 九维、阻断、血缘 | 屏蔽产品评价后独立评分 |

## 9. 新的停止门

### 9.1 真人页面开放前

任一条件出现即停止开门：

- 用户控制存在已知误判。
- 状态机或来源回放失败。
- 付费结果可能丢失。
- 陈旧提交可以串轮。
- 行为源码未进入指纹。
- 页面活动分支与产品决定不一致。
- 供应商特殊能力尚未通过兼容探针。
- 当前 run、版本或数据库状态无法准确回读。
- 全量测试仍有失败。

### 9.2 真人批次运行中

任一 P0 立即允许提前封存：

- 程序错误接管用户流程。
- 明确纠正未提交。
- 两个独立事件被污染。
- 已返回的有效结果丢失。
- 用户或 assistant 重复消息。
- 连续两个用户提交需要恢复。
- 人工第三次生成。
- 任务目标无法真实触发。
- 页面无法稳定保存、回看或导出。

### 9.3 可以继续采集

- 单条表达略重。
- 一次自动恢复在门限内成功。
- 孤立自然度问题。
- 不影响状态、用户控制和目标触发的轻微 UI 问题。

采集状态和 gate 状态分开：批次可以继续收集证据，同时明确显示已 No-Go。

## 10. 协作方式的新版约定

### 10.1 讨论阶段

每次只围绕一个关键产品选择，先说：

1. 用户看到了什么。
2. 为什么发生。
3. 对体验和评测有什么影响。
4. 有哪些解法。
5. 推荐方案和代价。

产品负责人确认后，再输出正式计划。

### 10.2 执行阶段

一次授权包写清：

- 代码和文档范围。
- Preview 部署和建批范围。
- 模型调用预算。
- 数据库范围。
- Production 边界。
- 最终停止点。

授权包内持续执行，中间只汇报进度和新的事实。新的产品选择、超预算模型调用、Production 变化或破坏性动作才触发暂停。

### 10.3 每次结论的四句话

1. 发生了什么。
2. 这对当前测试意味着什么。
3. 下一步处理什么。
4. 其余问题处于什么状态。

技术字段放在证据区，帮助产品负责人先得到可执行判断。

### 10.4 会话交接

每次换会话只依赖本地事实源：Map、当前 README、manifest、唯一问题台账、真实 run 和执行任务。侧边讨论中的决定要在当前会话收口时写回正式交接。

## 12. 最终经验清单

1. 真人时间只用于真人才能判断的体验和内容。
2. 评测页面属于测量仪器，仪器故障会污染全部结果。
3. 高影响程序接管追求高精度、明确对象和完整证据。
4. 测试全绿证明实现符合规则，产品反例门证明规则符合用户。
5. 技术完整、内容质量和端到端体验分账。
6. 任务执行、目标触发和质量通过分账。
7. 模型输出语义变化，程序维护确定状态。
8. Provider 结果先落账，业务状态随后可重入提交。
9. 客户端负责呈现，服务端负责调用资格、次数、截止和幂等。
10. 供应商特殊能力先做最小兼容探针。
11. 小探针用于选方向，连续真人轨迹用于判稳定性。
12. 单因素用于因果实验，已确认的底座问题可以合并修复。
13. 程序保护既是安全成功，也是端到端失败事件。
14. 提前结束是成熟的评测决策，需要正式状态和部分导出支持。
15. 每个 Bad Case 都要进入唯一问题台账和回归资产。
16. 候选版本与真人 run 分离，历史 run 永久只读。
17. 指纹覆盖真实行为闭包，部署证明绑定不可变源码。
18. 授权按执行包管理，范围内持续推进。
19. 产品结论先说人话，技术证据随后展开。
20. Production、Preview、模型调用和真人发布证据始终保持独立边界。

## 13. 对整个项目最有价值的最终判断

GI-088 的价值已经超出“找到一个更会提问的模型”。这轮实操建立了一套更接近真实 AI 产品的认知：模型给出语义能力，程序提供确定性和可靠性，评测工具保护真人劳动，证据治理保证每一次失败都能持续产生价值。

下一阶段最值得追求的指标，也需要从“测试通过了多少”升级为：

- 真人进入页面前，程序可确定问题清零率。
- 首次可见回答成功率。
- 已落账 Provider 结果丢失数。
- 错误程序接管数。
- 陈旧提交触发调用数。
- 真人一次批次被底座问题阻断的概率。
- 一次 Bad Case 转化为回归资产的完成率。

当这些指标稳定后，最终 12 项才能真正测量访谈质量，也才能为板块 7 正式接入和后续 Production 讨论提供可信证据。
